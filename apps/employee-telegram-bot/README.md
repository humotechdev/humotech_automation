# employee-telegram-bot

Telegram-бот сотрудника HUMOTECH на aiogram 3.

## Что он делает

Меню из десяти пунктов: личный кабинет, «я сейчас в офисе?», статистика
за сегодня, неделю и месяц, история посещений, больничный, отпуск, мои
заявки и помощь. Плюс разбор ссылки привязки и отправка уведомлений
из очереди.

Ни одной цифры бот не считает. Все они приходят из тех же endpoint'ов
`/api/v1/me/*`, которыми пользуется Mini App: иначе «за неделю» в чате
и «за неделю» на экране разошлись бы, и выяснить, какая цифра верна,
было бы нечем.

## Как он авторизуется

Никак — в том смысле, что токенов сотрудников не существует. На каждый
запрос бот шлёт два заголовка:

    X-Bot-Token         общий секрет с backend
    X-Telegram-User-Id  подтверждённый Telegram ID

Кто это, решает backend, и решает заново каждый раз. Разбиралось два
варианта, и второй выбран сознательно:

1. короткоживущий session token на сотрудника;
2. доверенный запрос на каждое действие.

У session token есть срок, и пока он не истёк, он работает после того,
как HR отключил привязку. Хранить его пришлось бы либо в памяти процесса
(теряется при перезапуске, живёт дольше нужного), либо в базе — то есть
завести таблицу секретов, которую надо чистить и отзывать. Здесь отзывать
нечего: «отключил» значит «сразу».

Без верного секрета `X-Telegram-User-Id` — просто число из запроса, и
backend его не читает. Ни `employee_id`, ни `organization_id` бот не знает
и не передаёт: их нет ни в одном ответе.

## Запуск

```bash
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt
cp .env.example .env        # заполнить BOT_TOKEN и BACKEND_BOT_SECRET
python -m src.check_config  # проверка настроек, без сети
python -m src.main
```

Тесты:

```bash
pip install -r requirements-dev.txt
pytest                      # 51 тест, без сети и без Telegram
```

## Уведомления

Очередь живёт в PostgreSQL на стороне backend. Подключения к базе у бота
нет и не будет: он спрашивает `/api/v1/telegram/bot/outbox`, получает
готовую пачку и отчитывается о результате. Захват строк
(`SELECT ... FOR UPDATE SKIP LOCKED`) делает backend — там есть транзакция.

Адресата бот не выбирает: `chat_id` приходит готовым, взятым из текущей
привязки сотрудника. Ошибиться адресатом ему нечем.

### Отправщик выбирается при запуске

`NOTIFICATIONS_SENDER` — `telegram` (по умолчанию) или `stub`.

`stub` — отправщик изолированного стенда: он не ходит наружу вовсе и не
поднимает диспетчер aiogram, потому что живой `Bot` начинает опрашивать
Telegram сразу, и подмена отправщика перестала бы что-либо значить.
`NOTIFICATIONS_STUB_FAIL` перечисляет типы, которые заглушка объявляет
неудачными: без этого нельзя проверить ни повтор, ни исчерпание попыток.

Настоящий токен в такой процесс не передаётся: заглушка сверяет форму
`BOT_TOKEN` и отказывается стартовать, если он похож на настоящий.

Значение по умолчанию боевое намеренно — забытая переменная должна
означать «отправляем по-настоящему», а не молчащую очередь.

Зачем это устроено так и как поднять стенд:
[`docs/development/isolated-checks.md`](../../docs/development/isolated-checks.md).

## Структура

```
src/api/selfservice.py     единственная дорога во внешний мир
src/middlewares/employee.py кто пишет боту — спрашивается на каждом апдейте
src/handlers/start/         разбор ссылки привязки
src/handlers/menu/          десять пунктов меню
src/messages/employee.py    тексты и перевод ответов API в сообщения
src/notifications/worker.py цикл очереди: забрать, отдать, отчитаться
src/notifications/sender.py  кто уносит наружу: Telegram или заглушка
```

Бизнес-логики в хендлерах нет: решение о том, можно ли что-то, принимает
сервер. ИИ здесь тоже нет — «Помощь» это статический текст.
