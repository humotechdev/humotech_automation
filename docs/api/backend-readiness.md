# Готовность бэкенда к React CRM

Список для того, кто садится писать фронтенд: что уже есть, чем это
проверено и чего ждать не стоит.

Проверять по нему можно самому — все команды ниже выполняются в
`apps/backend-api`.

---

## 1. Чем проверяется, что бэкенд жив

```
python manage.py check --deploy --settings config.settings.production
python manage.py makemigrations --check --dry-run
python manage.py spectacular --fail-on-warn --validate --file schema.yaml
python -m pytest
```

Ни одна из четырёх не должна ничего сказать. Последняя — 1012 тестов на
настоящем PostgreSQL с pgvector: подмены на SQLite нет, и это проверяет
отдельный предохранитель в `conftest.py`.

Сверка схемы с эталоном Alembic включается переменной:

```
ALEMBIC_BASELINE_URL=postgresql://…/humotech_baseline python -m pytest django_tests/test_schema_parity.py
```

Без переменной этот тест пропускается — на машине, где старой базы нет,
набор не должен падать по этой причине.

## 3. Что гарантировано во всём API

* **`organization_id` от клиента не принимается нигде.** Организация и
  область видимости определяются сервером по авторизованному
  пользователю.
* **Чужая организация отвечает как отсутствие записи** (`404`), свой
  объект вне области — отказом (`403`). Иначе перебором идентификаторов
  можно пересчитать записи соседей.
* **Пустая область — это «ничего», а не «всё».**
* **Формат ошибки один на всё API**: `{"error": {"code", "message",
  "details"}}`. Различать ситуации нужно по `code`: текст переводится.
* **Постраничный вывод keyset-овый**, курсором. Номеров страниц нет:
  между запросами данные меняются, и по номеру одна запись показалась бы
  дважды, а другая не показалась бы вовсе.
* **Каждое изменение попадает в журнал** — и через API, и через админку
  Django. Записи админки помечены префиксом `admin.` в поле `action`.
* **Секретов в журнале нет**: фильтр работает на составе полей, а не на
  добросовестности вызывающего.

## 4. Что нужно поднять рядом с бэкендом

| Процесс | Зачем | Без него |
| --- | --- | --- |
| `export-worker` | собирает фоновые выгрузки | заказы висят в `QUEUED` |
| бот | забирает очередь уведомлений | сообщения не уходят |
| `index_knowledge` | считает эмбеддинги | база знаний не участвует в ответах |

Первые два в `docker-compose.local.yml` уже описаны. Третий требует
включённого ассистента и ключа провайдера.

## 5. Чего ждать не стоит

Честный список, чтобы не искать:

* самостоятельной смены пароля и сброса по ссылке — отправлять её
  некуда, почтового канала в проекте нет;
* приглашения пользователя в CRM: учётная запись заводится и включается
  администратором вручную;
* двухфакторной аутентификации — колонка `mfa_enabled` в схеме есть,
  проверок за ней нет;
* загрузки документов базы знаний файлом: текст передаётся строкой,
  разбора DOCX и PDF нет;
* хранилища выгрузок в S3: файлы лежат на диске, адаптер не написан;
* ответов ассистента сотрудникам, пока `AI_ASSISTANT_ENABLED=false`.

## 6. С чего начать фронтенду

1. `POST /api/v1/auth/login` — организация, почта, пароль. Ответ
   устанавливает сессионную cookie; изменяющие запросы после этого
   требуют заголовка CSRF.
2. `GET /api/v1/auth/me` — роли и **список разрешений**. По нему
   скрываются недоступные разделы. Скрытая кнопка — удобство, а не
   защита: решение всё равно принимает сервер при каждом вызове.
3. `GET /api/schema` — генерация типов.
4. `GET /api/v1/dashboard` — главный экран одним запросом; каждая
   карточка несёт адрес, по которому виден её состав.
