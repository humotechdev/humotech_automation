# API HR CRM: всё, что нужно фронтенду

Документ описывает REST API кадровой системы так, чтобы по нему можно
было писать React CRM, не открывая исходники бэкенда.

Машиночитаемая схема: **`GET /api/schema`** (OpenAPI 3, YAML). При
`DEBUG=1` доступны читалки: **`/api/docs`** (Swagger UI) и **`/api/redoc`**.
В бою читалок нет намеренно — это лишний открытый интерфейс; сама схема
доступна всегда, по ней генерируются типы.

Схема и этот документ дополняют друг друга. Схема точна в путях, методах,
параметрах и типах. Документ объясняет то, чего из типа не видно: почему
`percent` бывает `null`, что означает пустое `late_minutes` и какие
переходы статусов разрешены.

## 1. Базовые правила

### Адреса и версия

Всё API живёт под `/api/v1/`. Версия зафиксирована в пути: клиентов
несколько (CRM, Telegram-бот, Mini App), обновляются они не одновременно.

Наборы действий (`regions`, `offices`, `employees`, `work-schedules`,
`qr-points`, `telegram/invitations`) собраны роутером DRF и требуют
**завершающего слэша**: `/api/v1/employees/`, `/api/v1/employees/{id}/`.
Отдельные адреса (`/api/v1/dashboard`, `/api/v1/attendance/presence`)
слэша не имеют. Это видно в схеме; при расхождении Django ответит `301`
на правильный адрес.

### Время

* Хранится и отдаётся в **UTC**, в формате ISO 8601 с указанием пояса:
  `2026-03-10T04:00:00+00:00`.
* Даты — `ГГГГ-ММ-ДД`.
* Границы суток считаются **в поясе офиса**, а не сервера и не браузера.
  Пояс всегда назван в ответе рядом с данными (`timezone`,
  `period.timezone`). «Сегодня» в Худжанде и в Душанбе — разные вопросы.
* Длительности — **в секундах**. Ни «8 ч 30 мин», ни «8.5»: округление
  и склонение зависят от места показа, а сервер, округлив однажды,
  теряет разницу навсегда.

### `organization_id`

**Клиент его не передаёт нигде и ни в каком виде.** Организация и область
видимости определяются сервером по авторизованному пользователю. Поле,
пришедшее от клиента, будет проигнорировано.

### Формат ошибок

Один на всё API:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Параметр «date» должен быть датой в формате ГГГГ-ММ-ДД",
    "details": { "field": "date", "value": "вчера" }
  }
}
```

| `code` | HTTP | Что означает |
| --- | --- | --- |
| `validation_error` | 400 | Некорректные входные данные; `details` называет поле |
| `unauthorized` | 401 | Нет сессии или она истекла |
| `forbidden` | 403 | Нет разрешения либо объект вне области видимости |
| `not_found` | 404 | Записи нет **либо** она принадлежит другой организации |
| `conflict` | 409 | Состояние не позволяет операцию (повторное решение, занятый код) |

Про `404`: чужая организация отвечает **так же**, как отсутствие записи.
Это сделано намеренно — иначе перебором идентификаторов можно пересчитать
записи соседей. Внутри своей организации объект вне области видимости
даёт `403`: скрывать факт его существования незачем.

### Постраничный вывод

Keyset, а не номера страниц:

```json
{ "items": [ ... ], "next_cursor": "eyJjcmVhdGVkX2F0Ijo...", "has_more": true }
```

* `limit` — от 1 до **200**, по умолчанию 50.
* `cursor` — берётся из `next_cursor` предыдущего ответа, никогда не
  собирается на клиенте.
* Номеров страниц нет: между двумя запросами кто-то создаёт сотрудника,
  и при `OFFSET` одна запись показалась бы дважды, а другая пропала.

Исключение — `/attendance/presence`: страниц у него нет. По нему
считаются карточки дашборда, а итог по первым пятидесяти строкам — не
итог, поэтому `counts` и `total` всегда по всему найденному составу.

У самого списка при этом есть жёсткий потолок в 500 строк: у
администратора офиса область видимости и правда ограничивает размер, а у
`HR_ADMIN` она — вся организация. Если строк оказалось больше, приходит
`"truncated": true` — `counts` и `total` остаются верными, а список
нужно сузить: `office_id`, `region_id`, `department_id` или `state`.

## 2. Авторизация: сессия Django, не JWT

### Порядок входа

1. `GET /api/v1/auth/me` — если вернулось `200`, сессия жива, вход не
   нужен. При `401` идём дальше.
2. Получить CSRF-cookie. Любой GET-запрос к API устанавливает
   `csrftoken`; отдельного адреса для этого нет.
3. `POST /api/v1/auth/login`:

```json
{ "organization_code": "HUMO", "email": "hr@humotech.tj", "password": "..." }
```

**Почта уникальна внутри организации**, поэтому `organization_code`
обязателен: одной пары «почта + пароль» для опознания недостаточно.

Ответ:

```json
{
  "id": "…", "email": "hr@humotech.tj", "full_name": "Иванова Мария",
  "organization_code": "HUMO",
  "permissions": ["employees.read", "employees.manage", "attendance.read"],
  "scopes": [{ "role": "REGIONAL_HR", "region_id": "…", "office_id": null }]
}
```

4. Все изменяющие запросы шлют заголовок `X-CSRFToken` со значением
   cookie `csrftoken` и `credentials: "include"`.
5. `POST /api/v1/auth/logout` завершает сессию.

### Неудачный вход

Ответ одинаков для несуществующей почты, неверного пароля и
заблокированной учётной записи: **`403` без объяснения причины**. Иначе
перебором почт выясняется, кто работает в компании. Ограничение частоты
на входе стоит отдельно.

### Что показывать в интерфейсе

`permissions` из `/auth/me` — единственный источник правды для того,
какие кнопки рисовать. **Скрытая кнопка ничего не защищает**: права
проверяет сервер на каждом запросе, а фронтенд только не показывает
заведомо недоступное.

## 3. Права и область видимости

Две независимые вещи:

* **Разрешение** отвечает на вопрос «что можно делать» — `employees.read`,
  `attendance.correct`, `reports.export`.
* **Область** (`scopes`) отвечает на вопрос «с чьими данными».

```
region_id = null и office_id = null  →  вся организация
указан region_id                      →  все офисы этого региона
указан office_id                      →  только этот офис
```

**Пустая область — это «ничего», а не «всё».** Пользователь с
`employees.read` и областью на регион без офисов не видит никого. Это
проверено отдельными тестами в каждом домене.

### Разрешения по доменам

| Домен | Чтение | Изменение |
| --- | --- | --- |
| Регионы | `regions.read` | `regions.manage` |
| Офисы | `offices.read` | `offices.manage` |
| Сотрудники | `employees.read` | `employees.manage`, увольнение — `employees.archive` |
| Графики | `schedules.read` | `schedules.manage` |
| Посещаемость | `attendance.read` | `attendance.correct` (решения), `attendance.manual` (ручная отметка) |
| QR-точки | `qr_points.read` | `qr_points.manage` |
| Отсутствия | `absences.read` | `absences.approve`, документы — `absences.documents` |
| Telegram | `telegram.read` | `telegram.manage` |
| Аналитика | `analytics.read` | — |
| Аналитика по сотруднику | `analytics.read` **и** `employees.read` | — |
| Выгрузки | `reports.export` **и** право на данные | — |
| Аудит | `audit.read` | запись через API невозможна |

Полный каталог — `humotech/core/permissions_catalog.py`.

## 4. Дашборд

### `GET /api/v1/dashboard`

Параметры: `date`, `office_id`, `region_id`, `department_id`,
`position_id`, `schedule_id`.

```json
{
  "date": "2026-03-10",
  "timezone": "Asia/Dushanbe",
  "cards": [
    {
      "key": "in_office",
      "title": "Сейчас в офисе",
      "value": 34,
      "endpoint": "/api/v1/attendance/presence",
      "params": { "date": "2026-03-10", "office_id": "…", "state": "IN_OFFICE" },
      "attention": false
    }
  ],
  "warnings": [
    {
      "code": "marks_during_absence",
      "title": "Отметки в дни оформленного отсутствия",
      "count": 2,
      "employee_ids": ["…", "…"]
    }
  ]
}
```

**`endpoint` и `params` подставляются как есть.** Не собирайте адрес
списка на клиенте: собранный вручную однажды разойдётся с тем, по
которому посчитано число, и никто этого не заметит. Число на карточке и
список по её адресу гарантированно совпадают — на это есть тест.

Карточки: `active_employees`, `should_work_today`, `came`, `in_office`,
`left`, `late`, `not_come`, `sick_leave`, `vacation`, `other_absence`,
`day_off`, `no_schedule`, `open_sessions`, `pending_requests`.

`attention: true` — на это стоит посмотреть. Не «плохо»: незакрытая
сессия может оказаться ночной сменой.

`active_employees` и `should_work_today` — **разные числа**. В штате сто
человек, а по графику сегодня выходят восемьдесят.

`pending_requests` равно нулю, если у пользователя нет `absences.read`:
карточка «12 заявок ждут» тому, кто не может открыть ни одну, — утечка
числа, а не сводка.

## 5. Посещаемость

### `GET /api/v1/attendance/presence` — кто где

Параметры: `date`, `office_id`, `region_id`, `department_id`,
`position_id`, `schedule_id`, `state`, `search`.

`counts` и `total` — по всему составу в области видимости. В `items`
попадает не больше 500 строк; когда их больше, приходит `"truncated":
true`, и список надо сузить фильтрами (числа при этом остаются верными).

```json
{
  "date": "2026-03-10",
  "timezone": "Asia/Dushanbe",
  "counts": { "IN_OFFICE": 34, "LEFT": 12, "NOT_COME": 3, "SICK_LEAVE": 1, "…": 0 },
  "total": 50,
  "truncated": false,
  "items": [
    {
      "employee_id": "…", "full_name": "Рахимов Далер",
      "employee_number": "EMP-0042",
      "office_id": "…", "office_name": "Головной офис",
      "department_name": "Разработка", "position_name": "Инженер",
      "state": "IN_OFFICE",
      "first_entry_at": "2026-03-10T04:02:00+00:00",
      "last_exit_at": null,
      "seconds": 18120,
      "open_session_id": "…",
      "late_minutes": 2,
      "scheduled_start": "09:00:00",
      "absence_code": null, "absence_name": null,
      "conflicting_marks": false
    }
  ]
}
```

#### Состояния (`state`)

| Значение | Что означает |
| --- | --- |
| `IN_OFFICE` | есть незакрытая сессия |
| `LEFT` | приходил и ушёл |
| `NOT_COME` | рабочий день по графику, отметок нет |
| `DAY_OFF` | нерабочий день по графику или праздник |
| `SICK_LEAVE` / `VACATION` / `OTHER_ABSENCE` | оформленное отсутствие |
| `NO_SCHEDULE` | **графика нет — судить не о чем** |

`NO_SCHEDULE` отделено от `NOT_COME` намеренно: ненастроенный справочник
не должен превращаться в обвинение человеку. Показывайте его как задачу
кадровику («назначьте график»), а не как прогул.

Отсутствие сильнее присутствия: человек на больничном, приложивший
пропуск, останется `SICK_LEAVE`, но получит `conflicting_marks: true`.
Это повод разобраться — больничный задним числом, чужая отметка или
ошибка в датах.

#### `late_minutes`

* `null` — **сравнивать не с чем**: нет графика или человек не приходил.
  Это не ноль.
* `0` — сравнение состоялось: пришёл вовремя или в пределах допуска.
* `> 0` — минуты **сверх** допуска `late_grace_minutes` из графика.
  При допуске 15 минут пришедший в 09:40 опоздал на 25, а не на 40.

Не показывайте `null` как «0 мин»: это разные утверждения.

### `GET /api/v1/attendance/events` — журнал сканирований

Только чтение. Параметры: `employee_id`, `office_id`, `region_id`,
`date_from`, `date_to`, `event_type` (`ENTRY`/`EXIT`), `source`
(`QR`/`MANUAL`/`IMPORT`), `verification_status`
(`ACCEPTED`/`REJECTED`/`REVIEW`), `cursor`, `limit`.

Отклонённые сканирования — это `verification_status=REJECTED`; причина
в поле `rejection_reason`.

**Метода изменения или удаления события не существует.** Сырая отметка
неизменяема: спор «во сколько человек пришёл» разрешается только записью,
которую нельзя было переписать.

Область считается по офису **самого события**, а не по текущему офису
сотрудника: после перевода человека его прошлые отметки остаются видны
администратору офиса, где они и сделаны.

### `GET /api/v1/attendance/sessions` — рабочие сессии

Параметры те же плюс `status` (`OPEN`/`CLOSED`/`CORRECTED`/`INVALID`) и
`open=true` (только незакрытые).

Незакрытая сессия имеет `ended_at: null` и `is_open: true`. **Выдуманного
времени выхода в ответе нет и не будет** — показывайте её как «идёт»,
а не как завершённую.

Сессия принадлежит дню своего **начала**. Ночная смена с 22:00 третьего
до 06:00 четвёртого целиком относится к третьему.

### Исправления

`GET /api/v1/attendance/corrections` — заявки сотрудников. Параметры:
`status`, `employee_id`, `office_id`, `region_id`, `cursor`.

`POST /api/v1/attendance/corrections/{request_id}/{decision}`, где
`decision` — `approve` или `reject`. Тело: `{ "comment": "…" }`.

Переходы: `SUBMITTED` | `IN_REVIEW` → `APPROVED` | `REJECTED`. Повторное
решение по рассмотренной заявке даёт `409`.

Одобрение меняет **расчётную сессию**, а не события. Прежние значения
остаются в журнале аудита.

### `POST /api/v1/attendance/manual` — ручная отметка

```json
{
  "employee_id": "…", "office_id": "…",
  "event_type": "ENTRY",
  "occurred_at": "2026-03-10T04:00:00+00:00",
  "reason": "Сломан экран у входа"
}
```

Создаёт **новое** событие с `source: "MANUAL"`. Причина обязательна и
не может быть пустой: по этим отметкам считают рабочее время.

## 6. Аналитика

### `GET /api/v1/analytics`

Область: без параметров — вся видимая; `region_id`, `office_id` или
`employee_id`. Период: `date_from`, `date_to` (по умолчанию текущий
месяц, не длиннее 366 дней). `series=false` отключает ряд по дням.

```json
{
  "scope": { "kind": "office", "id": "…", "name": "Головной офис" },
  "period": { "first": "2026-03-01", "last": "2026-03-31",
              "timezone": "Asia/Dushanbe" },
  "generated_at": "2026-04-01T09:15:00+00:00",
  "headcount": 50,
  "coverage": {
    "employees_total": 50, "employees_with_schedule": 47, "percent": 94.0,
    "note": "Норма рабочего времени считается только по сотрудникам с графиком…"
  },
  "totals": { "expected_working_days": 1034, "worked_seconds": 3348000, "…": 0 },
  "ratios": [
    {
      "key": "attendance", "title": "Посещаемость",
      "percent": 95.6, "numerator": 989, "denominator": 1034,
      "formula": "дни с отметками / рабочие дни по графику. Дни оформленного отсутствия исключены из обеих частей; сотрудники без графика не участвуют.",
      "unit": "days"
    }
  ],
  "series": [ { "day": "2026-03-02", "worked_seconds": 1620000,
                "attended": 47, "expected": 50, "late": 3 } ]
}
```

### Три правила, без которых цифры врут

**`percent: null` — это «нет данных», а не ноль.** Знаменатель нулевой:
в периоде не было рабочих дней, или ни у кого нет графика, или в области
нет сотрудников. Показывайте прочерк, а не «0%». Ноль процентов
утверждает «никто не приходил», и это утверждение попадёт в отчёт, по
которому принимают решения о людях.

**Всегда показывайте дробь рядом с процентом.** `numerator` и
`denominator` есть в каждом показателе именно для этого: «95,6%» не
отвечает ни на один вопрос, а «989 из 1034 рабочих дней» отвечает сразу
на все.

**`coverage` — это не украшение.** Если график есть у половины штата,
показатель посчитан по этой половине. Показывайте покрытие рядом с
цифрами, иначе неполнота справочника читается как уверенное число.

### Показатели

`totals`: `employees`, `expected_working_days`, `expected_seconds`,
`worked_seconds`, `attended_days`, `missed_days`, `sick_leave_days`,
`vacation_days`, `other_absence_days`, `late_arrivals`,
`late_minutes_total`, `open_sessions`, `rejected_scans`,
`overtime_seconds`, `undertime_seconds`,
`average_seconds_per_attended_day`.

`ratios`: `attendance`, `punctuality`, `worked_vs_expected`.

Переработка и недоработка — обе положительные: «−12 часов переработки»
читать неудобно.

**Ни один показатель не называется эффективностью или продуктивностью,
и не должен так называться в интерфейсе.** Система измеряет
посещаемость; о том, как человек работал, она не знает ничего.

### `GET /api/v1/analytics/compare`

`kind`: `region` | `office` | `period` (по умолчанию `office`).
Для областей — `left_id` и `right_id`. Для периодов — `date_from`/`date_to`
и `right_first`/`right_last`.

```json
{
  "kind": "office",
  "left":  { … полный отчёт … },
  "right": { … полный отчёт … },
  "differences": [
    {
      "key": "attendance", "title": "Посещаемость",
      "left":  { "percent": 95.6, "numerator": 989, "denominator": 1034 },
      "right": { "percent": 90.1, "numerator": 812, "denominator": 901 },
      "difference_points": 5.5,
      "difference_numerator": 177,
      "difference_denominator": 133,
      "comparable": true
    }
  ]
}
```

**`difference_points` — процентные ПУНКТЫ, а не проценты.** 95% против
90% — это 5 пунктов; «на 5% больше» было бы неправдой, потому что 5% от
90 равно 4,5. Подписывайте в интерфейсе «п. п.».

`comparable: false` означает, что у одной из сторон нулевой знаменатель
и разница не определена; `difference_points` в этом случае `null`.

## 7. Справочники

### Регионы, офисы, графики, сотрудники, QR-точки, отделы, должности

Общая форма набора действий (`{res}` — `regions`, `offices`, `employees`,
`work-schedules`, `qr-points`, `departments`, `positions`):

| Метод | Адрес | Что делает |
| --- | --- | --- |
| `GET` | `/api/v1/{res}/` | список: `search`, `status`, `limit`, `cursor` |
| `POST` | `/api/v1/{res}/` | создание |
| `GET` | `/api/v1/{res}/{id}/` | карточка |
| `PATCH` | `/api/v1/{res}/{id}/` | изменение |
| `POST` | `/api/v1/{res}/{id}/deactivate/` | выключение |
| `POST` | `/api/v1/{res}/{id}/reactivate/` | включение |

**Удаления нет ни у одного справочника.** На записи ссылаются отметки и
история; удаление означало бы потерю ответа на вопрос «где человек
приложил пропуск». Внешние ключи объявлены с `ON DELETE RESTRICT`, так
что база и не позволит.

Дополнительно:

* Офисы: `POST /offices/{id}/close/` — закрытие насовсем, необратимо.
  Фильтр списка: `region_id`.
* Сотрудники: `GET /employees/{id}/assignments/` (история назначений),
  `POST /employees/{id}/change-assignment/` (перевод),
  `POST /employees/{id}/terminate/` (увольнение, право
  `employees.archive`). Фильтры списка: `office_id`, `region_id`, `at`.
* Графики: `POST /work-schedules/{id}/assign/` — назначение сотруднику.
  `GET /employees/{id}/schedules` — история графиков сотрудника.
* Отделы: принадлежат офису, фильтры `office_id` и `region_id`. Права:
  чтение по `offices.read`, изменение по `departments.manage`. Иерархия
  не выходит за пределы одного офиса. `PATCH` меняет только название:
  код — часть договорённости с отчётами, а офис и родитель задают место
  в структуре, и менять их правкой поля значило бы переводить людей.
* Должности: принадлежат организации, не офису — «Инженер» один на всю
  компанию, и область видимости к ним не применяется. Чтение по
  `employees.read`, изменение по `positions.manage`.

### Статусы

| Сущность | Статусы |
| --- | --- |
| Регион, офис, график | `ACTIVE`, `INACTIVE`; офис ещё `CLOSED` (необратимо) |
| Сотрудник | `ACTIVE`, `SUSPENDED`, `TERMINATED` |
| Сессия | `OPEN`, `CLOSED`, `CORRECTED`, `INVALID` |
| Заявка (исправление, отсутствие) | `DRAFT`, `SUBMITTED`, `IN_REVIEW`, `APPROVED`, `REJECTED`, `CANCELLED` |
| Отсутствие | `PLANNED`, `ACTIVE`, `COMPLETED`, `CANCELLED` |

## 8. QR-точки

`GET/POST /api/v1/qr-points/`, `GET/PATCH /api/v1/qr-points/{id}/`,
`POST .../activate/`, `POST .../deactivate/`,
`POST .../reissue-token/`.

Фильтры списка: `office_id`, `region_id`, `is_active`, `search`.

Создание:

```json
{
  "office_id": "…", "code": "MAIN_ENTRANCE", "name": "Главный вход",
  "direction_mode": "BOTH", "qr_mode": "ROTATING", "rotation_seconds": 45
}
```

`direction_mode`: `ENTRY` | `EXIT` | `BOTH`.
`qr_mode`: `ROTATING` (код на экране меняется) | `STATIC` (наклейка).
`rotation_seconds`: от 5 до 300.

### Секрет статической точки

Ответ на создание и на перевыпуск — **единственное место, где виден
секрет**:

```json
{ "point": { … }, "static_token": "kJ8s...длинная-строка" }
```

**Показать его можно ровно один раз.** В базе только хеш; ни карточка,
ни список его не отдают и даже не знают о таком поле. Забыли записать —
перевыпускайте.

В интерфейсе: показать секрет один раз, с кнопкой «скопировать» и явным
предупреждением, что второй раз его не будет. Не кладите его в
`localStorage` и не логируйте.

Перевыпуск поднимает `token_version`: коды прошлой версии перестают
работать немедленно. Это и нужно, когда наклейку сфотографировали.

Режим точки (`qr_mode`) через `PATCH` **не меняется**: переключение
статической в поворотную — это выпуск или отзыв секрета, отдельная
операция с другими последствиями.

## 9. Отсутствия

### Со стороны кадровика

`GET /api/v1/absence-requests/pending` — заявки, ждущие решения.
`POST /api/v1/absence-requests/{request_id}/{decision}`, где `decision` —
`approve` или `reject`.

### Правила — настройка организации, а не код

Политика читается из `organization_settings` (`humotech/absences/policy.py`):
требуется ли подтверждение HR, нужна ли справка и с какого дня, разрешено
ли продление, можно ли отменить до рассмотрения, требует ли отмена
подтверждения после одобрения, допустимы ли отрицательные остатки.

Фронтенд получает действующие правила из `GET /api/v1/me/absences/options`
(для Mini App) и **не должен зашивать их в код**: у разных организаций
они разные.

### Остаток отпуска

Считается в минутах и списывается транзакционно, с блокировкой строки
баланса. Двойное подтверждение одной заявки не спишет дни дважды.

Отмена одобренной заявки возвращает дни в **израсходованное**, а не в
резерв: после подтверждения резерв уже переехал, и вычитание из нуля
молча потеряло бы отпуск.

## 10. Telegram

`GET/POST /api/v1/telegram/invitations/` — выдача персональных ссылок.
`GET /api/v1/telegram/invitations/pending/` — ожидающие подтверждения.
`POST /api/v1/telegram/invitations/{id}/confirm/` | `/reject/` | `/revoke/`.
`GET /api/v1/employees/{id}/telegram` — состояние привязки в карточке.
`POST /api/v1/employees/{id}/telegram/disconnect` — отключение.

Права: `telegram.read` и `telegram.manage`. Они отдельны от
`employees.manage` намеренно: правка карточки меняет данные о человеке,
а подтверждение привязки открывает ему **вход в систему**.

Отозванная привязка отвечает клиенту неотличимо от непривязанной. Иначе
перебором можно узнать, работает ли в компании владелец конкретного
Telegram-аккаунта.

## 11. Выгрузки

`GET /api/v1/reports/{kind}/export`

`kind`: `employees` | `attendance` | `sessions` | `summary`.
`fmt`: `csv` (по умолчанию) | `xlsx`.

> Параметр называется **`fmt`**, а не `format`: имя `format` занято самим
> DRF под выбор рендерера, и запрос с ним не дойдёт до кода.

Требует `reports.export` **плюс** право на сами данные. Выгрузка не
обходит область видимости: строки собираются теми же сервисами, что и
экраны.

Ответ — файл во вложении (`Content-Disposition: attachment`). CSV
отдаётся потоком без ограничения размера; у XLSX предел 50 000 строк,
при превышении приходит `400` с предложением взять CSV — молча
обрезанный файл выглядит полным, и это хуже отказа.

Первые строки каждого файла — период, часовой пояс, фильтры, момент
формирования, автор и определения формул. Через месяц никто не вспомнит,
за какие даты выгружен файл, а решения по нему принимать будут.

## 12. Аудит

`GET /api/v1/audit-logs` — требует `audit.read`.

Параметры: `action` (точное значение или префикс: `attendance.` найдёт
всё по посещаемости), `entity_type` (имя таблицы: `regions`, `employees`,
`offices`, `office_qr_points`, `attendance_events`…), `entity_id`,
`actor_user_id`, `date_from`, `date_to`, `cursor`, `limit`.

```json
{
  "items": [{
    "id": "…", "action": "attendance.correction.reviewed",
    "entity_type": "attendance_correction_requests", "entity_id": "…",
    "occurred_at": "2026-03-10T09:00:00+00:00",
    "actor_user_id": "…", "actor_email": "hr@humotech.tj",
    "old_values": { "status": "SUBMITTED" },
    "new_values": { "status": "APPROVED" },
    "ip_address": "10.0.0.5", "user_agent": "Mozilla/5.0 …"
  }],
  "next_cursor": null, "has_more": false
}
```

**Записывать в журнал через API нельзя** — методов `POST`/`PATCH`/`DELETE`
не существует. Записи кладут сервисы в той же транзакции, что и само
изменение.

Пароли, токены и хеши вырезаются при записи. Секрет QR-точки в журнал
не попадает.

## 14. Типовые сценарии

### Главный экран

```
GET /auth/me                      → права, области, имя
GET /dashboard?date=2026-03-10    → карточки
клик по карточке → GET card.endpoint + card.params
```

Не собирайте адрес карточки сами.

### Экран офиса

```
GET /offices/{id}/
GET /attendance/presence?office_id={id}&date=…
GET /qr-points/?office_id={id}
GET /analytics?office_id={id}&date_from=…&date_to=…
```

### Разбор опозданий

```
GET /attendance/presence?office_id=…&date=…  → строки с late_minutes > 0
```

Помните: `late_minutes: null` — не опоздание, а отсутствие суждения.

### Исправление отметки

```
GET  /attendance/corrections?status=SUBMITTED
POST /attendance/corrections/{id}/approve   { "comment": "Проверено" }
GET  /audit-logs?entity_id={id}             → что именно изменилось
```

### Выгрузка сводки

```
GET /reports/summary/export?fmt=xlsx&date_from=2026-03-01&date_to=2026-03-31
```

## 15. Чего в API пока нет

Честный список, чтобы не искать:

* **Праздничный календарь** (`CalendarException`) — учитывается в
  расчётах, редактируется только через админку Django.
* **База знаний и AI** — сервисы есть (`humotech/ai_assistant/`), HTTP
  для CRM нет.
* **Уведомления** — очередь `outbox` работает, отдельного API для
  просмотра и повторной отправки нет.
* **Управление пользователями и ролями CRM** — только админка Django.
* **Фоновая выгрузка больших отчётов** — сейчас синхронная, с потоковым
  CSV; очереди задач в проекте пока нет.

Для всего перечисленного бизнес-логика на месте; недостаёт именно
HTTP-обёртки.
