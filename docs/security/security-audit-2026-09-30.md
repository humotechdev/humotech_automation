## 3. Матрица «роль → действие → область»

Разрешения — «что можно делать», область (`user_role_scopes`) — «с чьими данными». После §2.1 для действий записи они связаны: право действует только в территории того назначения, что его несёт.

**Системные роли и их права** (источник — каталог прав, сверено со стендом):

| Роль | Прав | Характер |
|---|---|---|
| SUPER_ADMIN | 47 | всё, включая `roles.manage`, `users.manage`, `settings.manage` |
| HR_ADMIN | 43 | весь кадровый контур; без `roles.manage`, `users.manage`, `settings.manage`, `qr_display.start` |
| REGIONAL_HR | 22 | кадровый контур в своей области; **есть** `employees.manage`, `absences.approve`, `attendance.correct`, `schedules.manage`, `onboarding.manage`, `telegram.manage`; **нет** `attendance.manual`, `roles.manage` |
| OFFICE_ADMIN | 14 | офис и QR‑экран: `attendance.manual/correct`, `qr_display.start`, `qr_points.manage`; **нет** `employees.manage` |
| MANAGER | 7 | смотрит свою команду; из записи — только `absences.approve` |
| ACCOUNTANT | 6 | чтение + `reports.export` |
| TECH_ADMIN | 11 | техническая: `users.manage`, `roles.manage`, `settings.manage`, `qr_points.manage`, `notifications.manage`; **нет** кадровых прав и чтения сотрудников |
| VIEWER | 9 | только чтение |

**Область (scope)** задаётся назначением: вся организация (`region=∅, office=∅`), регион (раскрывается во все свои офисы) или один офис. Три состояния различаются: «видит всё» (`all_offices`), «видит перечень», «не видит ничего» (пустая область ≠ вся организация).

**Ключевые действия × чем ограничены** (после §2.1):

| Действие | Право | Область (разрез по праву) | Доп. ограничение |
|---|---|---|---|
| Ручная отметка посещаемости | `attendance.manual` | офис назначения с этим правом | не себе (`self_attendance`) |
| Решение по исправлению/выездной | `attendance.correct` | офис назначения с этим правом | не себе |
| Правка карточки, перевод, архив | `employees.manage`/`archive` | офис/регион назначения с этим правом | чужая организация = «не найдено» |
| Решение по заявке отсутствия, справки | `absences.approve`/`documents` | область назначения с этим правом | не себе (раздел обязанностей) |
| **Выдача и отзыв ролей** | `roles.manage` | область назначения с этим правом; на всю организацию — только у неограниченного | нельзя выдать роль/область шире своей |
| Django Admin (`/admin/`) | — | только неограниченный SUPER_ADMIN | плюс список адресов шлюза |
| Чтение списков (сотрудники, отметки, отсутствия) | `*.read` | **объединённая** область всех назначений | см. §4, известное сужение |

Пример связи (проверен живым запросом): `combo` = REGIONAL_HR(регион R2) + VIEWER(вся организация, чтение). `employees.manage` есть только у REGIONAL_HR → правка карточки допустима **только** в офисах R2. В офисе региона R1 (виден лишь на чтение через VIEWER) — `403`.

## 6. Что можно проверить только на сервере компании

Стенд (самоподписанный TLS на `localhost`, порты на петле) не подтверждает рабочую конфигурацию. На сервере после выкатки нужно:

1. **TLS и сертификат.** Проверить рабочий сертификат (Let's Encrypt), протоколы (без TLS 1.0/1.1), заголовки безопасности на рабочем домене. Стенд с `local_certs` это не показывает.
2. **Закрытые порты.** Снаружи: открыты только 80/443. PostgreSQL (5432), служебный API бота, `/admin/` — недоступны. Проверить именно с внешнего адреса, не с сервера.
3. **`/admin/`.** Открыт только списку адресов `GATEWAY_ADMIN_ALLOW`; при пустом — `403` всем. Проверить с разрешённого и постороннего адреса.
4. **Разделение прав PostgreSQL в бою.** Убедиться, что рантайм ходит ролью `humotech_app` (строка подключения), а миграции — `humotech_owner`; `humotech_app` не может `CREATE ROLE/TABLE`. Доказательство на стенде есть (§2.7), но боевые пароли и `initdb` — на сервере.
5. **Бэкапы.** Включить по таймеру с хранением вне сервера, прогнать первый цикл **бэкап → восстановление на НОВУЮ изолированную базу → сверка**. На стенде рабочие тома не трогались.
6. **Нагрузка и SSE под реальным шлюзом.** Замерить задержку «Обращений» и поведение воркеров под нагрузкой на боевом nginx/Caddy.
7. **Ротация секретов.** Токен бота (BotFather) и секреты стенда — вручную, по `rotate-telegram-token.md`. Без отдельного разрешения внешние токены не отзывались.

Процедуры деплоя и проверки после него — `deploy/test-server/README.md`.

## 7. Runbook изолированного стенда (запуск/остановка)

Проект Compose: `humotech_sec`. Рабочий каталог: `D:\HUMO-sec-base\deploy\test-server`. Файлы: базовый `docker-compose.yml` + `override.yml` (петля, `local_certs`, бот‑заглушка) + `fixed.yml` (образ backend). Переменные — в `secstand/.env` (секреты стенда вымышленные, одноразовые).

Команда‑основа (одной строкой, три `-f`):
```
docker compose -p humotech_sec --env-file <secstand>/.env \
  -f D:/HUMO-sec-base/deploy/test-server/docker-compose.yml \
  -f <secstand>/override.yml -f <secstand>/fixed.yml <ДЕЙСТВИЕ>
```

| Действие | Что делает | Данные |
|---|---|---|
| `up -d` | поднять стенд | сохраняются |
| `up -d --no-deps backend events export-worker attendance-reminders onboarding-reminders` | пересоздать только backend и воркеры (после смены образа) | сохраняются |
| `run --rm migrate` | применить миграции | сохраняются |
| `stop` | остановить контейнеры | **сохраняются** |
| `start` | запустить остановленные | сохраняются |
| `down` | удалить контейнеры и сети | тома (БД, файлы) **сохраняются** |
| `down -v` | удалить контейнеры, сети **и тома** | ⚠️ **УДАЛЯЕТ данные стенда** (БД, загруженные файлы, кэш Caddy) |

**Удаляют данные:** только `down -v` (и ручное `docker volume rm`). `stop`/`down` без `-v` — нет. На стенде это безопасно (вымышленные данные), но та же команда на рабочем сервере снесёт боевую базу — там `-v` не применять.

Посев стенда: `python manage.py shell -c "exec(open('/seed/seed.py').read())"` (вымышленные SECA/SECB, роли всех видов, пароль в `/tmp/secstand.json`). Пересев очищает и наполняет заново.
