## 3. Матрица «роль → действие → область»

Разрешения — «что можно делать», область (`user_role_scopes`) — «с чьими данными». После §2.1 для действий записи они связаны: право действует только в территории того назначения, что его несёт.

**Системные роли и их права** (источник — каталог прав, сверено со стендом):

| Роль | Прав | Характер |
|---|---|---|
| SUPER_ADMIN | 47 | всё, включая `roles.manage`, `users.manage`, `settings.manage` |
| HR_ADMIN | 43 | весь кадровый контур; без `roles.manage`, `users.manage`, `settings.manage`, `qr_display.start` |
| REGIONAL_HR | 22 | кадровый контур в своей области; **есть** `employees.manage`, `absences.approve`, `attendance.correct`, `schedules.manage`, `onboarding.manage`, `telegram.manage`; **нет** `attendance.manual`, `roles.manage` |
| OFFICE_ADMIN | 14 | офис и QR‑экран: `attendance.manual/correct`, `qr_display.start`, `qr_points.manage`; **нет** `employees.manage` |
| MANAGER | 7 | смотрит свою команду; из записи — только `absences.approve` |
| ACCOUNTANT | 6 | чтение + `reports.export` |
| TECH_ADMIN | 11 | техническая: `users.manage`, `roles.manage`, `settings.manage`, `qr_points.manage`, `notifications.manage`; **нет** кадровых прав и чтения сотрудников |
| VIEWER | 9 | только чтение |

**Область (scope)** задаётся назначением: вся организация (`region=∅, office=∅`), регион (раскрывается во все свои офисы) или один офис. Три состояния различаются: «видит всё» (`all_offices`), «видит перечень», «не видит ничего» (пустая область ≠ вся организация).

**Ключевые действия × чем ограничены** (после §2.1):

| Действие | Право | Область (разрез по праву) | Доп. ограничение |
|---|---|---|---|
| Ручная отметка посещаемости | `attendance.manual` | офис назначения с этим правом | не себе (`self_attendance`) |
| Решение по исправлению/выездной | `attendance.correct` | офис назначения с этим правом | не себе |
| Правка карточки, перевод, архив | `employees.manage`/`archive` | офис/регион назначения с этим правом | чужая организация = «не найдено» |
| Решение по заявке отсутствия, справки | `absences.approve`/`documents` | область назначения с этим правом | не себе (раздел обязанностей) |
| **Выдача и отзыв ролей** | `roles.manage` | область назначения с этим правом; на всю организацию — только у неограниченного | нельзя выдать роль/область шире своей |
| Django Admin (`/admin/`) | — | только неограниченный SUPER_ADMIN | плюс список адресов шлюза |
| Назначение графика, ознакомление, привязка Telegram, ответ на обращение, повтор рассылки | `schedules.manage`, `onboarding.manage`, `telegram.manage`, `questions.answer`, `notifications.manage` | область назначения с этим правом | то же правило, что и выше |
| Чтение списков (сотрудники, отметки, отсутствия) | `*.read` | **объединённая** область всех назначений | осознанно: чтение своей области через доп. назначение допустимо |

Пример связи (проверен живым запросом): `combo` = REGIONAL_HR(регион R2) + VIEWER(вся организация, чтение). `employees.manage` есть только у REGIONAL_HR → правка карточки допустима **только** в офисах R2. В офисе региона R1 (виден лишь на чтение через VIEWER) — `403`.

## 6. Что можно проверить только на сервере компании

Стенд (самоподписанный TLS на `localhost`, порты на петле) не подтверждает рабочую конфигурацию. На сервере после выкатки нужно:

1. **TLS и сертификат.** Проверить рабочий сертификат (Let's Encrypt), протоколы (без TLS 1.0/1.1), заголовки безопасности на рабочем домене. Стенд с `local_certs` это не показывает.
2. **Закрытые порты.** Снаружи: открыты только 80/443. PostgreSQL (5432), служебный API бота, `/admin/` — недоступны. Проверить именно с внешнего адреса, не с сервера.
3. **`/admin/`.** Открыт только списку адресов `GATEWAY_ADMIN_ALLOW`; при пустом — `403` всем. Проверить с разрешённого и постороннего адреса.
4. **Разделение прав PostgreSQL в бою.** Убедиться, что рантайм ходит ролью `humotech_app` (строка подключения), а миграции — `humotech_owner`; `humotech_app` не может `CREATE ROLE/TABLE`. Доказательство на стенде есть (§2.7), но боевые пароли и `initdb` — на сервере.
5. **Бэкапы.** Включить по таймеру с хранением вне сервера, прогнать первый цикл **бэкап → восстановление на НОВУЮ изолированную базу → сверка**. На стенде рабочие тома не трогались.
6. **Нагрузка и SSE под реальным шлюзом.** Замерить задержку «Обращений» и поведение воркеров под нагрузкой на боевом nginx/Caddy.

Сюда НЕ относится **серверный сертификат, внешний firewall, корпоративный proxy, серверные бэкапы по таймеру и производительность компании** — их проверяют на соответствующем сервере.

Процедуры деплоя и проверки после него — `deploy/test-server/README.md`.

### 6а. Ротация токена бота — не зависит от сервера компании (действие владельца)

Перевыпуск токена бота можно и нужно выполнить сейчас, отдельно от сервера: это действие в BotFather + правка `.env` + перезапуск сервисов. Полная инструкция владельцу — `docs/security/rotate-telegram-token.md`:
1. BotFather → `/revoke` → новый токен (старый умирает сразу);
2. вписать новый токен в `apps/employee-telegram-bot/.env` и `apps/backend-api/.env`;
3. `docker compose up -d --force-recreate bot <backend+workers>`;
4. проверка нового: `check_config`, логи без `401`, ручной `/start` и Mini App;
5. **проверка смерти старого**: `getMe` старым токеном → `401`.

Агент реальные токены не отзывает и значений не печатает. Самоподписанный локальный токен стенда — отдельный, боевого не касается.


| Действие | Что делает | Данные |
|---|---|---|
| `up -d` | поднять стенд | сохраняются |
| `up -d --no-deps backend events export-worker attendance-reminders onboarding-reminders` | пересоздать только backend и воркеры (после смены образа) | сохраняются |
| `run --rm migrate` | применить миграции | сохраняются |

| `start` | запустить остановленные | сохраняются |
| `down` | удалить контейнеры и сети | тома (БД, файлы) **сохраняются** |

### 10.2. §2 — стажировка и тип INTERN (на итоговом бэкенде)

- Трудовой статус PROBATION удалён полностью. Тип занятости INTERN оставлен как
  **устаревшее значение «только для чтения»** для существующих записей; создавать
  и назначать его нельзя (`OFFERED_EMPLOYMENT_TYPES` + `_validate_employment_type`).
- **Найдена и исправлена регрессия (форма перевода CRM).** Первая динамическая
  проверка на уровне службы (в контейнере итогового бэкенда, в откаченной
  транзакции) показала: `change_assignment` с явным `employment_type=INTERN` →
  400. А форма перевода CRM (`NewEmployeePage.tsx:764`) присылает **текущий** тип
  занятости при любом изменении назначения, и у существующего INTERN это
  неизменный `INTERN`. Значит такого сотрудника **нельзя было перевести** (другой
  офис/должность) — он бы получал 400. Это нарушение §2 «существующих не ломать».
  **Правка:** `change_assignment` теперь валидирует тип только при его фактической
  СМЕНЕ (`changes["employment_type"] != current.employment_type`). Ввести INTERN
  заново по-прежнему нельзя (это смена значения → 400). **Проверена вся цепочка:**
  сериализатор `AssignmentChangeSerializer.employment_type` — `CharField` без
  `choices` (INTERN не режется на уровне DRF), а форма CRM в режиме правки не
  гоняет шаговую валидацию и проверяет лишь непустоту — значит клиент INTERN не
  блокирует и перевод доходит до исправленной службы.
- **Поведение после правки** (юнит-тесты в `test_hr_employees.py` на исправленном
  коде, образ `backend:test` монтирует итоговый код; плюс исходная проверка на
  уровне службы):

  | Сценарий | Ожидание | Факт |
  |---|---|---|
  | Существующий INTERN → смена офиса без `employment_type` | проходит, тип сохранён | ✅ |
  | Существующий INTERN → перевод, форма шлёт неизменный INTERN | проходит, INTERN сохранён | ✅ (после правки) |
  | `change_assignment` со СМЕНОЙ типа на INTERN | 400 | ✅ 400 «Недопустимый тип занятости» |
  | `create` с INTERN | 400 | ✅ 400 |
  | `create` с FULL_TIME | 201 | ✅ |
  | `create` со статусом PROBATION | 400 | ✅ 400 |

  Вывод: **существующих сотрудников блокировка не ломает** (переводятся, тип
  сохраняется), а создать/назначить новый INTERN или статус PROBATION нельзя.
- *Замечание по отображению:* в исходниках CRM нет подписи для INTERN (0
  упоминаний), поэтому у существующего INTERN-сотрудника в карточке тип покажется
  сырым кодом/пусто. Это косметика; окончательно снимается решением владельца по
  14 записям (ниже). В Mini App подпись INTERN→«стажёр» для чтения есть.
- Бэкап-таблица `employees_probation_backup` помечена **временной** (докстринг
  миграции 0010); окончательное удаление — отдельным шагом
  `humotech/employees/sql/drop_probation_backup.sql` (выполняет владелец на проде).
- **Доказательство на изолированной копии РЕАЛЬНЫХ данных** (копия рабочей
  `humotech_e2e`, не сама рабочая БД): 207 сотрудников целы → миграции 0010/0011/
  0007/0008 применились → **14 PROBATION→ACTIVE, 14 INTERN сохранены**, снимок 18
  строк → `drop_probation_backup.sql` → **0** бэкап-таблиц / **0** probation-колонок /
  **0** PROBATION / **0** PROBATION_END. Копия удалена. Рабочую БД не меняли (read-only).
- **Перечень существующих записей (§2, без ПДн).** В локальной e2e-БД
  `humotech_e2e` (это демо-сид, табельные `HT-0101…0300`; `HT-0001/0002` —
  демо-ключевые) ровно **14 «стажёров»** — статус PROBATION + тип INTERN на

  ```sql
  SELECT e.employee_number, e.employment_status, a.employment_type, a.valid_from

  JOIN employees e ON e.id = a.employee_id
  WHERE a.employment_type = 'INTERN' OR e.employment_status = 'PROBATION'
  ```
