# Целостность журнала аудита (`audit_logs`)

Уровни защиты, по возрастанию силы:

1. **Модель** `AuditLog` (`apps/backend-api/humotech/audit/models.py`) запрещает правку и удаление через ORM-объект.
2. **Триггер БД** `audit_logs_append_only` (миграция `audit/0002`): UPDATE запрещён (кроме обнуления
   `actor_user_id` внутренним триггером ON DELETE SET NULL при удалении учётки), DELETE — только в транзакции
   с `SET LOCAL humotech.audit_purge = 'on'` (так чистят журнал сидеры изолированных стендов,
   `humotech/audit/purge.py`). Защищает от ошибок кода и обходов модели (`QuerySet.update/delete`, сырой SQL
   по ошибке), **но не от скомпрометированной роли приложения**: такая роль может сама выставить флаг.
3. **Права роли приложения на рабочем сервере (рекомендация серверной команде, не применено):**
   ```sql
   REVOKE UPDATE, DELETE ON audit_logs FROM humotech_app;
   ```
   На рабочем сервере сидеры не запускаются, поэтому удаление журнала приложению не нужно; ссылочное
   действие ON DELETE SET NULL выполняется с правами владельца таблицы и продолжит работать.
   В `deploy/test-server/initdb` это не включено намеренно: там же разворачиваются стенды с пересозданием
   демо-данных.
4. **Внешняя копия:** регулярная выгрузка журнала в хранилище с запретом удаления (object lock) —
   единственная защита от администратора БД. Решение — за ИБ.

Открытый вопрос к ИБ и юристам: срок хранения журнала (в нём снимки ПДн карточки) — см.
`docs/audits/l9-retention-options.md`.
