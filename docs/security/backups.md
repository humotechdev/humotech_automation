# Резервное копирование и проверка восстановления

Скрипты: `infrastructure/backup/`.

| Файл | Что делает |
|---|---|
| `backup.sh` | дамп базы + архивы томов → шифрование → ротация → (опц.) отправка наружу |
| `restore-test.sh` | восстановление копии в одноразовый PostgreSQL и сверка |
| `lib.sh` | общие функции (настройки, шифрование) |
| `backup.env.example` | все настройки с пояснениями (локальный стенд) |
| `../../deploy/test-server/backup.env.example` | настройки **тестового сервера** (проект compose `humotech_test`) |
| `systemd/*.service`, `systemd/*.timer` | расписание |
| `tests/test-backup.sh` | проверки скриптов на изолированном окружении |

Пошаговая настройка тестового сервера — `deploy/test-server/README.md`,
раздел «Резервные копии».

## Откуда берутся база и тома

Два режима, выбираются настройками:

- **Проект Docker Compose** (`BACKUP_COMPOSE_PROJECT`, тестовый сервер):
  контейнер базы — запущенный контейнер с метками
  `com.docker.compose.project=<проект>` и
  `com.docker.compose.service=<BACKUP_PG_SERVICE>`; тома — по меткам
  `com.docker.compose.project` и `com.docker.compose.volume=<ключ>` для каждого
  ключа из `BACKUP_COMPOSE_VOLUMES`. Формат имён Compose («проект_том»,
  «проект-сервис-1») не угадывается. Для `humotech_test` это
  `humotech_test-postgres-1`, `humotech_test_private_media`,
  `humotech_test_private_exports` (проверено на поднятом стеке 25.09.2026).
- **Явные имена** (`BACKUP_PG_CONTAINER`, `BACKUP_VOLUMES`, локальный стенд):
  `humotech_postgres`, `docker_private_media`, `docker_private_exports`.

Ноль или больше одного найденного ресурса — ошибка, копия не начинается.

## Когда копия считается созданной

Копия собирается в `BACKUP_DIR/.partial-<время>` и переименовывается в
`BACKUP_DIR/<UTC-время>` **только после всех проверок**; только тогда скрипт
печатает путь к ней и выходит с кодом 0. Любая ошибка — код 1, строка
`ОШИБКА: …` в журнале, незавершённый каталог удаляется:

| Ситуация | Сообщение |
|---|---|
| контейнер базы не найден / остановлен | `контейнер … не найден` / `… есть, но не запущен` |
| обязательный том отсутствует | `том … НЕ НАЙДЕН — копия не создаётся` |
| том есть, но пуст, и не указан в `BACKUP_ALLOW_EMPTY_VOLUMES` | `том … существует, но ПУСТ — копия не создаётся` |
| том документов пуст, а база ссылается на файлы | `том документов … существует, но ПУСТ, а база ссылается на N живых файлов` |
| в томе документов файлов меньше, чем живых строк `files` | `в базе N живых файлов, а в томе … только M` |
| `tar` завершился с ошибкой | `архивация завершилась с ошибкой` |
| архив не распаковывается | `архив не распаковывается — копия повреждена` |
| `pg_dump` упал / дамп не читается | `pg_dump завершился с ошибкой` / `дамп не читается pg_restore` |

«Пустой том существует» и «том не найден» — разные сообщения намеренно.
Пустым разрешено быть тому выгрузок (они живут 72 часа) и тому документов на
новом сервере — пока в таблице `files` нет ни одной живой строки.

## Что копируется

- **База** `humotech_django`: `pg_dump -Fc` внутри контейнера базы через
  unix-сокет (пароль не нужен и нигде не передаётся), в транзакции
  `REPEATABLE READ, READ ONLY`.
- **Тома** с документами (справки, больничные, документы сотрудников) и
  выгрузками — `tar.gz` из вспомогательного контейнера, тома подключены
  только на чтение. Каждый архив сразу распаковывается во вспомогательном
  контейнере и пересчитывается: `volume-<том>.sha256` — SHA-256 каждого
  файла архива.
- **Манифест** `manifest.tsv`: число строк в каждой таблице, миграции по
  приложениям, версии расширений, число живых строк `files`, число файлов в
  каждом томе и настоящее имя тома, отметка `status complete`.
  Счётчики берутся **из того же снимка базы**, что и дамп
  (`pg_export_snapshot` → `pg_dump --snapshot`), поэтому при проверке они
  сравниваются на точное равенство, даже если во время копирования шли
  отметки.
- `SHA256SUMS` на все файлы копии.

Не копируются: `staticfiles` (пересобирается `collectstatic`), `.env`
(секреты хранятся отдельно — в менеджере паролей владельца, не рядом с
бэкапом), образы Docker (пересобираются из репозитория).

## Шифрование

Каждый файл копии шифруется **открытым ключом** до того, как покинет
каталог копирования:

- **age** (рекомендуется): на сервере только `BACKUP_AGE_RECIPIENT`
  (`age1...`). Закрытый ключ (`AGE-SECRET-KEY-...`) создаётся на машине
  владельца (`age-keygen -o humotech-backup.key`), хранится офлайн — в
  менеджере паролей и на бумаге/USB в сейфе — и **на сервер не кладётся**.
  Украденная с сервера или из хранилища копия без него бесполезна.
- **gpg**: то же через `BACKUP_GPG_RECIPIENT` (открытый ключ в keyring root).
- `none` — только для локальных копий на стенде; отправку наружу скрипт в
  этом режиме не выполняет.

Потеря закрытого ключа = потеря всех копий. Ключей лучше два
(`BACKUP_AGE_RECIPIENTS_FILE` с двумя получателями): у владельца и у
второго ответственного.

## Хранение вне сервера

`BACKUP_REMOTE_ENABLED=false` по умолчанию. Включение:

1. Бакет в S3-совместимом хранилище **у другого провайдера / в другом
   регионе**, чем сервер.
2. Отдельный ключ доступа только к этому бакету; по возможности — право
   только на запись (без удаления) и **Object Lock / версионирование** на
   срок ≥ 30 дней. Тогда взломанный сервер не сможет стереть старые копии
   (защита от шифровальщиков).
3. Настройки rclone — переменными `RCLONE_CONFIG_<ИМЯ>_*` в
   `/etc/humotech/backup.env` (образец в `backup.env.example`), никаких
   `rclone.conf` в репозитории.
4. `BACKUP_REMOTE_ENABLED=true`, `BACKUP_RCLONE_REMOTE=offsite:bucket/prod`.
   Скрипт делает `rclone copy --immutable`, затем `rclone check`, затем
   удаляет во внешнем хранилище копии старше `BACKUP_REMOTE_KEEP` (90 дней).
   Если ключ без права удаления — удаление завершится ошибкой; тогда
   `BACKUP_REMOTE_KEEP=0` и срок хранения задаётся правилом жизненного
   цикла бакета.

## Ротация

На сервере (`BACKUP_DIR=/var/backups/humotech`, права 700):
последние **14** ежедневных копий + первая копия каждого из **6** последних
месяцев. Во внешнем хранилище — 90 дней (или правило бакета).

## Расписание

### systemd (рекомендуется)

```bash
sudo install -d -m 700 /etc/humotech
# тестовый сервер: deploy/test-server/backup.env.example; локальный стенд: infrastructure/backup/backup.env.example
sudo install -m 600 deploy/test-server/backup.env.example /etc/humotech/backup.env   # и заполнить
sudo cp infrastructure/backup/systemd/humotech-*.{service,timer} /etc/systemd/system/
# в .service путь к репозиторию: /opt/humotech — поправьте, если другой
sudo systemctl daemon-reload
sudo systemctl enable --now humotech-backup.timer
systemctl list-timers 'humotech-*'
sudo systemctl start humotech-backup.service && journalctl -u humotech-backup -n 30
```

- `humotech-backup.timer` — ежедневно в 02:30 (±10 мин), `Persistent=true`:
  пропущенный из-за выключения запуск выполнится при старте.
- `humotech-restore-test.timer` — 1-го числа в 05:00. Включать **там, где
  есть закрытый ключ** (см. ниже), обычно не на боевом сервере.

Сбой сервиса нужно видеть: подключите `OnFailure=` к своему способу
оповещения (почта, Telegram-бот администратора) или мониторьте
`systemctl is-failed humotech-backup.service`.

### cron (если systemd недоступен)

```cron
# /etc/cron.d/humotech-backup
30 2 * * *  root  BACKUP_CONFIG=/etc/humotech/backup.env /opt/humotech/infrastructure/backup/backup.sh >>/var/log/humotech-backup.log 2>&1
0  5 1 * *  root  BACKUP_CONFIG=/etc/humotech/backup.env /opt/humotech/infrastructure/backup/restore-test.sh >>/var/log/humotech-restore-test.log 2>&1
```

## RPO и RTO

| | Цель | Чем обеспечено |
|---|---|---|
| **RPO** (сколько данных можно потерять) | ≤ 24 ч | ежедневная копия 02:30 |
| **RTO** (за сколько поднять) | ≤ 4 ч | дамп восстанавливается за минуты; основное время — новый сервер, Docker, `.env` из менеджера паролей |

Если потеря дня отметок недопустима — следующий шаг не «чаще pg_dump», а
непрерывная архивация WAL (pgBackRest / WAL-G) в то же внешнее хранилище:
RPO сокращается до минут. Для текущего объёма это избыточно.

## Проверка восстановления — ежемесячно

Копия, которую ни разу не восстанавливали, копией не считается.

`restore-test.sh [каталог копии]` (по умолчанию — последняя в `BACKUP_DIR`):

1. сверяет `SHA256SUMS` — ловит повреждение файлов. От подмены копии
   целиком суммы без подписи не защищают: это обеспечивают Object Lock и
   ключ хранилища «только запись»;
2. расшифровывает дамп (`BACKUP_AGE_IDENTITY_FILE` или gpg-ключ);
3. поднимает **одноразовый** `pgvector/pgvector:pg18` — случайное имя,
   случайный пароль, без опубликованных портов, во внутренней сети
   `--internal`; рабочая база не затрагивается вовсе;
4. `pg_restore --exit-on-error`;
5. сравнивает число строк **всех** таблиц, миграции по приложениям и
   расширения (`vector`, `btree_gist`) с манифестом — на равенство;
6. если задан `BACKUP_VERIFY_APP_IMAGE` — `manage.py migrate --check`
   образом приложения: схема копии соответствует коду;
7. **восстанавливает файлы** каждого тома во временный том Docker и
   сверяет каждый файл по SHA-256 со списком, снятым при копировании
   (`sha256sum -c`), и число файлов с манифестом;
8. удаляет контейнер (вместе с анонимным томом данных), временные тома,
   сеть и расшифрованные файлы при любом исходе.

Копию без отметки `status complete` в манифесте (незавершённую или
созданную прежней версией скрипта) проверка не принимает.

Код выхода 0 и строка `ПРОВЕРКА ПРОЙДЕНА: … восстанавливается полностью
(база и файлы)` — копия пригодна.

Где запускать: на отдельной машине (ноутбук администратора, стенд), куда
копия забирается из внешнего хранилища (`rclone copy offsite:bucket/prod/<дата> ./`)
и где есть закрытый ключ. Так закрытый ключ никогда не лежит на боевом
сервере.

Ежемесячный регламент (15 минут):

1. Выбрать копию (последнюю из внешнего хранилища, раз в квартал — копию
   месячной давности).
2. Запустить `restore-test.sh <каталог>`; сохранить вывод (в нём только
   имена таблиц и числа, без содержимого).
3. Записать в журнал: дата, копия, `ПРОЙДЕНА/НЕ ПРОЙДЕНА`, время
   `pg_restore`, число сотрудников и событий отметок.
4. Раз в полгода — полная репетиция: поднять из копии весь стенд
   (backend + CRM) на отдельной машине и войти в CRM. Замерить фактическое RTO.

### Автоматические проверки скриптов

`infrastructure/backup/tests/test-backup.sh` — одноразовый PostgreSQL и тома
с метками Compose под случайным именем проекта, вымышленные данные; всё
удаляется после прогона. Случаи: тома на месте (один пустой — разрешён) →
копия и полное восстановление базы и файлов; подменённый файл в архиве при
верных `SHA256SUMS` → проверка ловит; том не найден; том пуст без
разрешения; том документов пуст при живых файлах в базе; ошибка `tar`;
испорченный архив при нулевом коде `tar`; режим явных имён; новый сервер без
файлов; остановленная база. Во всех случаях отказа проверяется, что нет ни
готового каталога, ни `.partial`.

## Восстановление в бою (кратко)

Тестовый сервер — готовые команды в `deploy/test-server/README.md`, раздел
«Восстановление стека из копии». Общий порядок:

1. Остановить сервисы, пишущие в базу и тома:
   `docker compose ... stop backend bot export-worker attendance-reminders onboarding-reminders gateway`.
2. Расшифровать файлы копии на машине с ключом, передать на сервер.
3. Пересоздать базу и восстановить дамп:
   ```bash
   docker compose exec -T postgres dropdb -U humotech humotech_django
   docker compose exec -T postgres createdb -U humotech -O humotech humotech_django
   docker compose exec -T postgres pg_restore -U humotech -d humotech_django --no-owner --exit-on-error < db.dump
   ```
4. Тома: очистить (`find /dst -mindepth 1 -delete`), распаковать
   `volume-<том>.tar.gz` и сверить `sha256sum -c < volume-<том>.sha256`
   (для пустого тома список пуст — сверять нечего). Имя тома — по меткам
   `com.docker.compose.project` / `com.docker.compose.volume`.
5. `docker compose ... up -d` — `migrate` доведёт схему, если код новее копии.
6. Удалить расшифрованные файлы (`shred -u`).
