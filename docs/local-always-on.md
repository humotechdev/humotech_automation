# Постоянный локальный стенд HUMOTECH

Временный тестовый контур: весь HUMOTECH работает на ноутбуке, а снаружи
доступен по одному постоянному адресу. Позже эта же схема переносится на
Linux-сервер — почти без изменений, см. последний раздел.

## Постоянный адрес

```
https://hr-dev.humotech.com
```

Он не меняется никогда: ни при перезапуске контейнеров, ни при
перезагрузке Windows, ни при переустановке Docker. Адрес принадлежит
именованному туннелю Cloudflare и живёт на их стороне, а не в этих
файлах.

Отсюда главное следствие: **кнопку Telegram-бота больше не нужно
обновлять**. Она указывает на постоянный адрес; бот сверяет её при
каждом старте и переписывает, только если она смотрит не туда.

По одному адресу отдаётся всё:

| Путь | Что там |
|---|---|
| `/` | Mini App сотрудника |
| `/api/v1/` | API backend |
| `/admin/` | Django Admin |
| `/static/` | статика админки |
| `/health/live` | процесс жив |
| `/health/ready` | база доступна, расширения на месте, миграции применены |

Один origin выбран намеренно: браузер не видит межсайтового запроса,
CORS не участвует, и `TELEGRAM_MINI_APP_ALLOWED_ORIGINS` остаётся
пустым — закрытым, как и задумано.

Приложенные файлы (справки, больничные) через веб-сервер **не
раздаются**. Медицинский документ отдаёт view, который сначала
спрашивает, кому можно. Каталог лежит вне `MEDIA_URL`, и маршрута к нему
в nginx нет.

## Что запускается

Шесть контейнеров, все в одной внутренней сети Docker:

| Контейнер | Роль | Наружу |
|---|---|---|
| `humotech_postgres` | PostgreSQL 18 + pgvector | только `127.0.0.1:5433` |
| `humotech_migrate` | разовый: миграции и `collectstatic` | нет |
| `humotech_backend` | Django под gunicorn, 3 воркера | нет |
| `humotech_bot` | Telegram-бот, long polling | нет |
| `humotech_gateway` | nginx: Mini App + обратный прокси | нет |
| `humotech_cloudflared` | Cloudflare Tunnel | исходящее соединение |

Наружу не опубликован ни один сервис. Единственный вход снаружи —
туннель, и он смотрит на `gateway:80` внутри сети Docker. PostgreSQL
доступен только с самого ноутбука, по петлевому адресу.

### Чего здесь нет и почему

Отдельных worker-контейнеров в стеке нет — не по недосмотру:

* **очередь уведомлений** разбирает сам бот. Он спрашивает
  `/api/v1/telegram/bot/outbox`, получает пачку и отчитывается о
  результате; захват строк делает backend. Отдельный процесс-отправщик
  в этой схеме не существует;
* **очередь выгрузок** пока без исполнителя: таблица `export_jobs`
  заведена, а worker, endpoint'ы и потоковая запись XLSX ещё не
  написаны. Пустой контейнер, которому нечего запускать, хуже его
  отсутствия;
* **AI-ассистент** выключен (`AI_ASSISTANT_ENABLED=false`), платных
  обращений наружу не выполняется, индексация запускается командой
  `manage.py index_knowledge` вручную.

Когда worker выгрузок появится, он добавляется в
`docker-compose.local.yml` отдельным сервисом с тем же образом
`humotech/backend:local` и своей командой.

## Первоначальная настройка

Делается один раз.

### 1. Cloudflare

Домен `humotech.com` уже обслуживается Cloudflare — переносить ничего не
нужно.

1. `one.dash.cloudflare.com` → **Networks → Tunnels → Create a tunnel →
   Cloudflared**, имя, например `humotech-local`, → **Save**.
2. В показанной команде установки есть `--token eyJ…`. Эта длинная
   строка и есть токен; нужна только она, без `--token`.
3. Вкладка **Public Hostname → Add a public hostname**:
   * Subdomain: `hr-dev`
   * Domain: `humotech.com`
   * Path: пусто
   * Type: **HTTP**
   * URL: **`gateway:80`**
4. **Save hostname**. CNAME Cloudflare создаёт сам.

`gateway:80` — это имя сервиса в `docker-compose.local.yml`.
Переименование сервиса сломает туннель и потребует правки в панели.

### 2. Токен

```powershell
copy infrastructure\docker\.env.example infrastructure\docker\.env
```

и вписать в `.env`:

```
PUBLIC_HOSTNAME=hr-dev.humotech.com
CLOUDFLARE_TUNNEL_TOKEN=eyJ…
```

Файл в Git не попадает: шаблон `.env` в `.gitignore` закрывает его на
любой глубине. Токен туннеля равносилен праву опубликовать что угодно на
этом поддомене — в переписку его пересылать не нужно.

Остальные секреты остаются там же, где были: `apps/backend-api/.env` и
`apps/employee-telegram-bot/.env`. Стенд читает их как есть и
переопределяет только адреса, которые внутри сети Docker другие.

### 3. Автозапуск Docker

Docker Desktop → **Settings → General** → включить
**Start Docker Desktop when you sign in**.

Сейчас эта галочка **выключена**: в `%APPDATA%\Docker\settings-store.json`
стоит `"AutoStart": false`, и записи Docker в автозапуске Windows нет.
Пока она выключена, после включения ноутбука стенд не поднимется сам —
придётся запускать Docker Desktop руками. Галочку нужно поставить один
раз, через интерфейс: файл настроек Docker Desktop переписывает при
выходе, и правка его снаружи не переживёт перезапуск.

Этого достаточно. Контейнеры помечены `restart: unless-stopped` и
поднимаются сами, как только запустится Docker Engine. Задача в Windows
Task Scheduler не нужна; если Docker Desktop почему-то не стартует сам,
см. «Типичные ошибки».

### 4. Первый запуск

```powershell
powershell -ExecutionPolicy Bypass -File scripts\local-start.ps1 -Build
```

Первая сборка занимает несколько минут: ставятся зависимости Python и
собирается фронтенд. Дальше образы кэшируются.

## Обычный запуск

Ничего запускать не надо. Включили ноутбук, вошли в Windows, Docker
Desktop поднялся сам — контейнеры поднялись вместе с ним.

Если стенд останавливали руками (`local-stop.ps1`), обратно:

```powershell
scripts\local-start.ps1
```

Ручная остановка сильнее политики перезапуска: остановленный контейнер
Docker сам не поднимет.

## Обновление после правки кода

```powershell
scripts\local-update.ps1
```

Скрипт прогоняет тесты, пересобирает образы, применяет миграции и
перезапускает изменившееся. Адрес не меняется.

Порядок держит не скрипт, а compose: миграции выполняет отдельный
разовый сервис, и backend объявлен зависящим от его успешного
завершения. Поэтому «новый код на старой схеме» невозможен, и несколько
процессов не начнут применять миграции одновременно.

Есть одно исключение, и оно закрыто иначе. При автоматическом подъёме
после перезагрузки Docker поднимает контейнеры по их политике
перезапуска и `depends_on` не перечитывает — это правило только для
`docker compose up`. Поэтому backend может стартовать, не дожидаясь
сервиса миграций. Схема при этом не меняется сама по себе, а если она
всё же отстала, `/health/ready` отвечает 503 с числом непринятых
миграций, и контейнер не становится здоровым. Проблема видна сразу, а не
всплывает отдельными падающими запросами.

Пропустить тесты (не рекомендуется): `scripts\local-update.ps1 -SkipTests`.

## Статус и логи

```powershell
scripts\local-status.ps1          # цепочка снизу вверх, до публичного адреса
scripts\local-logs.ps1                        # последние строки всех сервисов
scripts\local-logs.ps1 -Service backend -Follow
```

`local-status.ps1` проверяет Docker, каждый контейнер, готовность
backend внутри контейнера и три публичных адреса. Первая красная строка
сверху и есть причина; всё, что ниже, обычно следствие.

## Резервное копирование PostgreSQL

Данные лежат в томе `docker_postgres_data`. Том переживает пересборку,
перезапуск и `docker compose down`, но не `down -v` — этой команды в
скриптах нет намеренно.

Снять копию:

```powershell
docker exec humotech_postgres pg_dump -U humotech -d humotech_django -Fc > backup.dump
```

Восстановить в чистую базу:

```powershell
docker exec -i humotech_postgres pg_restore -U humotech -d humotech_django --clean --if-exists < backup.dump
```

`--clean --if-exists` удаляет существующие объекты перед восстановлением.
На базе с данными это разрушительно; для проверки восстановления заводите
отдельную базу и указывайте её в `-d`.

Копия — это файл на том же диске, что и оригинал. Против отказа диска она
не помогает: переносите её наружу.

## Типичные ошибки

**`cloudflared` перезапускается по кругу.** Пустой или неверный
`CLOUDFLARE_TUNNEL_TOKEN` в `infrastructure/docker/.env`. Логи:
`scripts\local-logs.ps1 -Service cloudflared`.

**Публичный адрес отвечает 502.** Туннель жив, `gateway` — нет, либо в
панели Cloudflare указан не тот адрес сервиса. Должно быть ровно
`gateway:80`.

**`backend` не становится healthy.** Смотрите `local-logs.ps1 -Service
backend`. Частые причины: не отработали миграции (тогда `/readyz`
честно отвечает 503) и недоступная база.

**Каждый запрос отвечает редиректом.** Потерян заголовок
`X-Forwarded-Proto`. Django в боевых настройках включает
`SECURE_SSL_REDIRECT`, и без этого заголовка он бесконечно
перенаправляет запрос на самого себя. Заголовок ставит nginx
(`infrastructure/docker/gateway/proxy-headers.inc`).

**HTTP 400 на всех запросах.** `DJANGO_ALLOWED_HOSTS` не совпадает с
`PUBLIC_HOSTNAME`. Они задаются в одном месте — `.env` стенда.

**Порт 5433 занят.** На машине уже работает другой PostgreSQL или старый
контейнер. Системный сервер на 5432 стенд не трогает.

**Docker Desktop не стартует при входе.** Проверьте
Settings → General → Start Docker Desktop when you sign in. Если
галочка стоит, а он всё равно не поднимается, задачу в Task Scheduler
можно завести вручную — но не от имени администратора: Docker Desktop
работает от обычного пользователя, и задача с повышенными правами
запустит его в другом сеансе, где вы его не увидите.

## Что происходит при выключении и сне

Честно и без оговорок:

* **ноутбук выключен** — система недоступна. Ни Mini App, ни бот, ни
  уведомления;
* **сон или гибернация** — то же самое. Туннель обрывается, Telegram
  показывает ошибку загрузки;
* **нет интернета** — то же самое, даже если ноутбук работает;
* **закрыт Docker Desktop** — контейнеры останавливаются вместе с ним.

Уведомления не теряются: очередь живёт в PostgreSQL, и бот разберёт её,
когда стенд вернётся. Отметки по QR за время простоя сделать нельзя —
их просто некому принять.

Это временный контур для проверки. Для пилота в регионах нужен
постоянно работающий сервер: сотрудники приходят к восьми утра, и
доступность «пока ноутбук открыт» для этого не годится.

## Перенос на Linux-сервер

Схема готовилась с расчётом на переезд, поэтому меняется немногое:

1. те же два файла compose — они не содержат ничего, что привязано к
   Windows;
2. `infrastructure/docker/.env`: другой `PUBLIC_HOSTNAME` (например
   `hr.humotech.com`) и токен другого туннеля;
3. `cloudflared` остаётся, либо заменяется обычным TLS на 443 — тогда
   в nginx добавляется сертификат, а `X-Forwarded-Proto` он ставит уже
   сам;
4. пароль PostgreSQL и `DJANGO_SECRET_KEY` меняются на новые: те, что
   лежат в локальных `.env`, считаются известными;
5. вместо `restart: unless-stopped` — systemd-юнит, если нужен
   контролируемый порядок запуска относительно других служб;
6. резервное копирование по расписанию, а не руками.

Скрипты `local-*.ps1` при этом не переносятся: они про Windows. Их
эквивалент на сервере — `docker compose` напрямую или юнит systemd.
