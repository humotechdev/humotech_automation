# Привязка Telegram и вход в Mini App

Как сотрудник получает доступ к своим данным из Telegram — и почему именно так.

---

## Зачем вообще привязка

Бот и Mini App должны знать, КТО им пишет. Telegram сообщает только свой
идентификатор пользователя; связать его с конкретным сотрудником может лишь
тот, кто знает штат, — отдел кадров.

Отсюда весь порядок: систему открывает не сотрудник и не Telegram, а HR.

---

## Порядок целиком

```
HR                        сотрудник                 backend
 │                            │                        │
 │ создаёт ссылку ──────────────────────────────────►  │  токен: 256 бит
 │ ◄──── ссылка (один раз)                             │  в базе — только SHA-256
 │                            │                        │
 │ передаёт ссылку ─────────► │                        │
 │                            │ /start link_<ТОКЕН> ─► │  бот + секрет бота
 │                            │                        │  привязка = PENDING
 │                            │ ◄─ «ждёт подтверждения»│  ДОСТУПА ЕЩЁ НЕТ
 │ ◄─── очередь на подтверждение ───────────────────── │
 │ подтверждает ────────────────────────────────────►  │  привязка = ACTIVE
 │                            │                        │
 │                            │ открывает Mini App ──► │  initData -> токен
 │                            │ ◄──────── свои данные  │
```

### 1. HR создаёт ссылку

Карточка сотрудника → «Привязать Telegram».

```http
POST /api/v1/telegram/invitations/
{"employee_id": "..."}
```

Ответ — **единственное место во всей системе, где виден открытый токен**:

```json
{
  "invitation": {"id": "...", "status": "ACTIVE", "expires_at": "..."},
  "token": "0Xk8...43 символа",
  "link": "https://t.me/humotech_hr_bot?start=link_0Xk8..."
}
```

В базе лежит только SHA-256 от токена. Повторно показать ссылку невозможно
даже суперпользователю: сервер сам её не знает. Потерянная ссылка отзывается
и выдаётся заново — это дешевле, чем хранить рабочий секрет в таблице.

В ссылке нет ни идентификатора сотрудника, ни организации, ни персональных
данных — только случайный токен.

**Когда откажет:**

| Причина | Ответ |
|---|---|
| нет разрешения `telegram.manage` | 403 |
| сотрудник вне области видимости HR | 403 |
| сотрудник другой организации | 404 (как несуществующий) |
| сотрудник уволен или в архиве | 409 |
| у сотрудника уже есть привязка | 409 — сначала отключить |
| у сотрудника уже есть живая ссылка | 409 — сначала отозвать |

### 2. Сотрудник открывает ссылку

Бот получает `/start link_<ТОКЕН>` и делает ровно один вызов:

```http
POST /api/v1/telegram/bot/link
X-Bot-Token: <общий секрет>
{"token": "...", "telegram_user_id": 12345, "telegram_chat_id": 12345,
 "telegram_username": "ivan", "language_code": "ru"}
```

Ни сотрудника, ни организацию бот не передаёт: их определяет токен.

Результат — привязка в состоянии **PENDING**. Это ещё не доступ: ссылку можно
переслать, потерять, показать через плечо, и по ней привязывается тот, кто её
открыл. HR обязан увидеть, кто это был, прежде чем человек получит доступ.

Бот отвечает человеку по коду причины, а не по тексту: «срок истёк» и «уже
использована» требуют от него разных действий.

### 3. HR подтверждает

```http
GET  /api/v1/telegram/invitations/pending/
POST /api/v1/telegram/invitations/{id}/confirm/
POST /api/v1/telegram/invitations/{id}/reject/
```

В очереди виден `consumed_by_telegram_user_id` — тот самый идентификатор,
который пришёл от Telegram. Именно его HR и сверяет.

Только после `confirm` привязка становится **ACTIVE**.

### 4. Вход в Mini App

```http
POST /api/v1/telegram/mini-app/auth
{"init_data": "<window.Telegram.WebApp.initData целиком>"}
```

Больше в теле ничего нет и быть не может: `telegram_user_id`, `employee_id`,
`organization_id` не принимаются — подделать можно только то, что где-то
принимается.

## Как проверяется `initData`

Алгоритм Telegram, реализован в `humotech/telegram/initdata.py` отдельным
модулем без базы — чтобы его можно было прогнать по всем краям, не поднимая
ни организации, ни сотрудника.

```
secret_key = HMAC_SHA256(key="WebAppData", msg=<токен бота>)
ожидаемый  = HMAC_SHA256(key=secret_key, msg=data_check_string)
```

`data_check_string` — все пришедшие поля **кроме `hash`**, отсортированные по
имени, склеенные через `\n` в виде `ключ=значение`, значения уже раскодированы
из query-строки.

Что проверяется помимо самой подписи:

| Проверка | Почему |
|---|---|
| сравнение постоянного времени | обычное `==` выходит на первом несовпавшем байте — по времени ответа хеш подбирается побайтово |
| `auth_date` не старше 5 минут | просроченная строка — это перехваченная строка |
| `auth_date` не из будущего (допуск 60 с) | без верхней границы строка жила бы вечно; допуск — на расхождение часов |
| наличие `user` с `id` | Mini App из инлайн-режима приходит без него, и опознавать некого |
| токен бота задан | не задан — отказ, а не «пропустим на этот раз» |

`initDataUnsafe` не читается ни на сервере, ни в Mini App. Это те же поля, но
без подписи: любой, кто открыл страницу в браузере, подставит туда что угодно.

**Причина отказа наружу не выносится.** Все отказы выглядят одинаково: по
разнице ответов подбирается и состав полей, и срок. Код причины
(`bad_signature`, `expired`, `user_missing`, …) остаётся в журнале.

## Внутренний токен Mini App

Подписанная строка `django.core.signing` — не JWT и не новая таблица.

Почему так:

* **не JWT.** Своего механизма токенов в проекте нет, а заводить библиотеку
  ради одного endpoint'а незачем: подпись `SECRET_KEY` делает ровно то же;
* **не сессия Django.** CRM работает на cookie, но Mini App открывается по
  своему адресу — для браузера это third-party cookie, а их блокируют
  вебвью на iOS. Токен в заголовке работает везде;
* **не таблица токенов.** Хранить нечего: подпись сама удостоверяет
  содержимое.

Отзыв при этом работает **немедленно**, а не с истечением срока: на каждом
запросе перечитывается состояние привязки и сверяется `telegram_user_id` из
подписи с текущим значением в базе. Второе обязательно — строка привязки у
сотрудника одна и переиспользуется при перепривязке, поэтому её идентификатор
владельца не удостоверяет.

Класс аутентификации подключён **только** к endpoint'ам Mini App. Токеном
Mini App нельзя обратиться к кадровому API даже при ошибке в маршрутах:
`request.user` там — не модель пользователя, а `EmployeePrincipal`, из
которого `Actor` не собирается.

### Где токен хранится во frontend

В памяти, копия — в `sessionStorage`.

* `localStorage` **не используется**: он переживает закрытие Mini App и
  остаётся в вебвью неограниченно долго — на общем устройстве следующий
  человек открыл бы чужую сессию;
* одной памяти мало: перезагрузка страницы внутри вебвью не обновляет
  `initData` — строка сохраняет прежний `auth_date`, а он живёт пять минут.
  Без `sessionStorage` перезагрузка через пять минут после запуска означала
  бы «откройте приложение заново»;
* `sessionStorage` очищается вместе с вкладкой вебвью, то есть при закрытии
  Mini App — ровно та граница, которая здесь нужна.

Доступ к хранилищу обёрнут в `try`: в приватном режиме он бросает исключение,
и приложение из-за этого падать не должно — оно лишь теряет способность
пережить перезагрузку.

## Схема данных

### `telegram_accounts` — текущий доступ

Одна строка на сотрудника, навсегда. Перепривязка не создаёт новую строку,
а меняет эту: у доступа нет истории, у него есть только текущее состояние.

Статусы: `PENDING` → `ACTIVE` → `REVOKED`, плюс `BLOCKED`.
Значение `PENDING` добавлено на этом этапе.

Два безусловных уникальных ключа: сотрудник не может иметь двух Telegram,
Telegram не может принадлежать двум сотрудникам.

### `telegram_link_invitations` — история попыток

| Поле | Смысл |
|---|---|
| `token_hash` | SHA-256 от токена; уникален, по нему же идёт поиск |
| `status` | `ACTIVE` → `PENDING_CONFIRMATION` → `USED` / `REJECTED`; либо `REVOKED` / `EXPIRED` |
| `expires_at` | срок; статус `EXPIRED` материализуется, когда система на строку натыкается |
| `used_at`, `revoked_at`, `reviewed_at` | когда перешли, отозвали, решили |
| `consumed_by_telegram_user_id` | кто перешёл — это HR и сверяет |
| `created_by_user`, `reviewed_by_user` | кто выдал и кто решил |

Ограничения:

* `uq_telegram_link_invitations_token` — уникальность хеша;
* `uq_telegram_link_invitations_open_employee` — **частичный** уникальный
  индекс: у сотрудника не больше одной живой ссылки. Иначе HR, нажав дважды,
  рассылает две рабочие ссылки и не знает, какая у человека на руках;
* `ck_telegram_link_invitations_status` — допустимые статусы;
* четыре внешних ключа с явным `ON DELETE` (три `RESTRICT`, один `SET NULL`
  на `reviewed_by_user`: учётную запись HR можно заблокировать, но запись
  о принятом решении обязана остаться).

Почему медленный хеш (argon2) здесь не нужен: токен не пароль. Его выбирает
`secrets.token_urlsafe(32)` — 256 бит, перебирать нечего, а проверка идёт на
каждом переходе по ссылке. Медленный хеш стал бы способом положить сервер,
ничего не защитив.

## Что закрыто

| Угроза | Чем закрыта |
|---|---|
| утечка дампа базы даёт рабочие ссылки | в базе только SHA-256 |
| ссылка работает вечно | `expires_at`, по умолчанию сутки |
| ссылка работает дважды | статус меняется под блокировкой строки |
| два одновременных перехода | `select_for_update` + уникальные ключи в базе |
| по ссылке перешёл не тот | обязательное подтверждение HR |
| один Telegram у двух сотрудников | безусловный уникальный ключ |
| бот подделает Telegram ID | общий секрет `X-Bot-Token` |
| подделка `initData` | HMAC по алгоритму Telegram, сравнение постоянного времени |
| повтор перехваченной `initData` | `auth_date` не старше 5 минут |
| токен живёт после отключения привязки | состояние перечитывается на каждом запросе |
| вход уволенного | проверяется на входе и на каждом запросе |
| HR трогает чужих сотрудников | `user_role_scopes`, область считается на сервере |
| утечка между организациями | чужая организация отвечает как несуществующая запись |
| перебор | ограничение частоты на всех трёх входах |
| секреты в журналах | `AuditTrail.FORBIDDEN_FIELDS`, отдельный тест |

Область доступа **никогда** не берётся из запроса: переданный клиентом
`organization_id` не принимается ни одним endpoint'ом этого этапа — его
просто негде передать.

## Права

Два новых разрешения:

| Код | Что даёт |
|---|---|
| `telegram.read` | видеть состояние привязки и очередь на подтверждение |
| `telegram.manage` | выдавать ссылки, подтверждать, отклонять, отзывать, отключать |

Отдельно от `employees.manage` намеренно: правка карточки меняет данные о
человеке, а подтверждение привязки открывает ему вход. Право дать вход не
обязано прилагаться к праву исправить отчество.

Роли: `SUPER_ADMIN`, `HR_ADMIN`, `REGIONAL_HR` — оба; `OFFICE_ADMIN` — только
чтение. Уже развёрнутым базам разрешения доливает миграция
`rbac/0002_telegram_permissions`.

## Endpoint'ы

| Метод и путь | Кто | Что |
|---|---|---|
| `POST /api/v1/telegram/invitations/` | HR | создать ссылку |
| `GET /api/v1/telegram/invitations/` | HR | список (фильтры `employee_id`, `status`) |
| `GET /api/v1/telegram/invitations/pending/` | HR | ожидают подтверждения |
| `POST /api/v1/telegram/invitations/{id}/confirm/` | HR | подтвердить |
| `POST /api/v1/telegram/invitations/{id}/reject/` | HR | отклонить |
| `POST /api/v1/telegram/invitations/{id}/revoke/` | HR | отозвать неиспользованную |
| `GET /api/v1/employees/{id}/telegram` | HR | состояние привязки |
| `POST /api/v1/employees/{id}/telegram/disconnect` | HR | отключить привязку |
| `POST /api/v1/telegram/bot/link` | бот | погасить ссылку |
| `POST /api/v1/telegram/mini-app/auth` | Mini App | `initData` → токен |
| `GET /api/v1/telegram/mini-app/me` | Mini App | свои данные |

Состояние в карточке одним словом: `NOT_LINKED`, `INVITED`, `PENDING`,
`ACTIVE`, `REVOKED`.

## Запуск локально

### 1. База

```bash
docker compose -f infrastructure/docker/docker-compose.yml up -d
```

### 2. Backend

```bash
cd apps/backend-api
cp .env.example .env          # заполнить TELEGRAM_*
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
.venv/Scripts/python.exe manage.py migrate --settings=config.settings.development
.venv/Scripts/python.exe manage.py seed --create-organization HUMO --settings=config.settings.development
.venv/Scripts/python.exe manage.py runserver --settings=config.settings.development
```

### 3. Бот

```bash
cd apps/employee-telegram-bot
cp .env.example .env          # BOT_TOKEN, BOT_USERNAME, BACKEND_BOT_SECRET
.venv/Scripts/python.exe -m src.check_config    # проверка без обращений наружу
PYTHONPATH=. .venv/Scripts/python.exe -m src.main
```

### 4. Mini App

```bash
cd apps/employee-mini-app
npm install
npm run dev                   # http://localhost:5174, запросы к /api проксируются
```

### Обязательные переменные

**backend-api:** `DJANGO_DATABASE_URL`, `DJANGO_SECRET_KEY`,
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_BOT_API_SECRET`,
`TELEGRAM_MINI_APP_ALLOWED_ORIGINS` (для браузерных клиентов).

**bot:** `BOT_TOKEN`, `BOT_USERNAME`, `BACKEND_BOT_SECRET`, `API_MODE=live`,
`BACKEND_API_URL`.

**mini-app:** `VITE_API_URL`.

`TELEGRAM_BOT_TOKEN` в backend и `BOT_TOKEN` в боте — **один и тот же токен**.
`TELEGRAM_BOT_API_SECRET` и `BACKEND_BOT_SECRET` — тоже одно значение.
Не совпадут — привязка отвечает 403.

## Что осталось на следующие этапы

Сознательно не делалось:

* **QR-вход и выход.** Сервис отметок уже есть и уже определяет сотрудника
  по привязке Telegram — не хватает бот-интерфейса и экрана QR;
* **личный кабинет Mini App.** Есть только защищённая заглушка: вход
  работает, показывать пока нечего;
* **токен доступа для самого бота.** Mini App входит через `initData`;
  боту нужен свой обмен, чтобы показывать отметки и заявки. До него разделы
  бота остаются заглушками на прежнем контракте;
* **уведомление «HR подтвердил привязку».** Канала backend → bot не
  существует; порт под него зарезервирован (`BOT_INTERNAL_PORT`), но ничего
  не слушает. Пока сотрудник узнаёт о подтверждении, открыв Mini App;
* больничные, отпуска, AI-ассистент, аналитика, полный интерфейс CRM.

Ни один тест не обращается в Telegram: строка `initData` подписывается тем же
алгоритмом локально, заведомо ненастоящим токеном бота.

Тест гонки помечен `transaction=True` — иначе два потока не видят записей друг
друга, `select_for_update` блокируется на пустом месте, и тест проходит, ничего
не проверив. Он откалиброван: со снятой блокировкой падает.
