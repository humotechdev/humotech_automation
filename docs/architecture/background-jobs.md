# Фоновые процессы: три очереди без брокера

В проекте нет Celery, Redis и RabbitMQ, и это решение, а не отставание.
Брокер добавил бы ещё один процесс, ещё одно место, где сообщение может
потеряться, и ещё одну систему, которую надо поднимать вместе со
стендом. Взамен нужна была одна гарантия — «не сделать того, чего не
происходило, и не потерять того, что произошло», — и её даёт транзакция
PostgreSQL.

Все три очереди устроены одинаково: таблица заданий, захват строки через
`SELECT ... FOR UPDATE SKIP LOCKED`, отметка времени захвата на случай
падения исполнителя.

| Очередь | Таблица | Исполнитель |
| --- | --- | --- |
| Отправка уведомлений | `notifications` | бот по HTTP (`/api/v1/telegram/bot/outbox`) |
| Индексация базы знаний | `knowledge_index_jobs` | `manage.py index_knowledge` |
| Фоновые выгрузки | `export_jobs` | `manage.py run_export_worker` |

`SKIP LOCKED` нужен ровно затем, чтобы два исполнителя не подрались за
одну строку и при этом не выстроились в очередь: второй просто берёт
следующую.

## Исполнитель выгрузок

### Запуск

```
python manage.py run_export_worker            # один проход и выход
python manage.py run_export_worker --loop=5   # постоянно, пауза 5 с
```

В Docker это отдельный сервис `export-worker` с `restart: unless-stopped`.
Отдельный процесс, а не поток внутри backend: сборка отчёта за год
занимает минуты и ест память, и делать это там, где одновременно
отвечают на запросы, значит подвесить интерфейс ради одного файла.

Ключа провайдера и выхода в интернет исполнителю не нужно: он читает
базу и пишет файл.

### Захват и работа — в разных транзакциях

Это отличается от индексации знаний, где они в одной, и отличается
намеренно. Там задача короткая. Здесь сборка длинная, и открытая всё это
время транзакция держала бы блокировку строки и снимок базы — на большой
выгрузке это раздувает журнал предзаписи.

Поэтому строка помечается `RUNNING` и коммитится сразу, а брошенную
работу возвращает `reclaim_stale` по `locked_at`: блокировка строки при
падении процесса снимается сама, статус — нет.

### Состояния

```
QUEUED ──захват──> RUNNING ──успех──> SUCCEEDED
   │                  │
   │                  ├─временный сбой──> QUEUED (попытка+1, пауза n² · база)
   │                  └─попытки кончились ИЛИ отказ по правам──> FAILED
   │
   └──отмена──> CANCELLED
```

**Отказ по правам не повторяется.** Права проверяются в момент сборки, и
«у автора больше нет доступа» повтором не лечится: вторая попытка
кончится ровно тем же, а попытки сгорят и настоящая причина потеряется.
К этому же классу относится превышение предела строк XLSX.

Всё остальное — сбой записи, недоступность базы — возвращается в очередь
с растущей паузой.

### Чьими правами собирается файл

Правами заказчика, **на момент сборки**. Заказ вчерашний, сборка
сегодняшняя, и роли за ночь могли измениться: кадровик, которого
перевели в один офис, не должен получить файл по всей компании потому,
что нажал кнопку до перевода.

Отсюда же правило скачивания: файл отдаётся только заказчику. Коллеге
с другой областью видимости он показал бы данные, закрытые для того на
экране, и никакой отдельной дыры для этого не потребовалось бы.

### Где лежит файл

Каталог задаётся `EXPORTS_PRIVATE_ROOT` и лежит **вне зоны раздачи
статики** — по той же причине, что и каталог справок о болезни: готовая
выгрузка это кадровые данные, и веб-сервер не должен отдавать их по
угаданному адресу. Файл выдаёт view, который сначала спрашивает, кому
можно.

Имя файла на диске — идентификатор задания плюс расширение, и только
оно. Ни имени отчёта, ни фильтров: имя видно в списке каталога, и
`zarplata-direktora.xlsx` рассказывает лишнее ещё до открытия. Ничто из
присланного клиентом в путь не попадает.

Хранилище берётся абстракцией Django (`FileSystemStorage`), а не работой
с путями напрямую: перевод на S3 не должен требовать правок в
прикладном коде. Самого адаптера S3 пока нет.

### Срок хранения

Файл удаляется через `EXPORTS_RETENTION_HOURS` часов после готовности —
именно после готовности, а не после заказа: задание могло простоять в
очереди, и файл, родившийся уже просроченным, никому не достался бы.

Убирает исполнитель сам, раз в шестьдесят проходов. Отдельно есть
команда:

```
python manage.py purge_exports
```

Запись задания при уборке остаётся: по ней видно, что выгрузка была и
кем заказана. Уходит только файл — именно он и есть утечка, отложенная
во времени.

### Настройки

| Переменная | Умолчание | Что означает |
| --- | --- | --- |
| `EXPORTS_PRIVATE_ROOT` | `private-exports` рядом с кодом | каталог готовых файлов |
| `EXPORTS_RETENTION_HOURS` | `72` | через сколько часов файл удаляется |
| `EXPORTS_MAX_ATTEMPTS` | `3` | после скольких неудач задание помечается FAILED |
| `EXPORTS_RETRY_BASE_SECONDS` | `60` | база растущей паузы между попытками |
| `EXPORTS_LOCK_TIMEOUT_SECONDS` | `900` | через сколько зависшее задание считается брошенным |
| `EXPORTS_POLL_INTERVAL_SECONDS` | `5` | пауза опроса очереди, когда работы нет |
| `EXPORTS_MAX_PENDING_PER_USER` | `5` | сколько незавершённых заказов держит один человек |

### Общий том — обязательное условие

Файл пишет `export-worker`, а отдаёт `backend`. В `docker-compose.local.yml`
оба монтируют том `private_exports` по одному и тому же пути. Разные тома
дали бы зелёные тесты и `404` при каждом скачивании: на одной машине,
где всё в одном процессе, такое не воспроизводится вовсе.

## Индексация базы знаний

```
python manage.py index_knowledge --loop=10
```

Команда отказывается запускаться при `AI_ASSISTANT_ENABLED=false` — это
защита от случайного обращения к платному провайдеру.

С той же стороны защищён и API: постановка задания отказывает кодом
`ai_disabled` или `provider_not_configured` и **не создаёт строку в
очереди**. Задание, которое некому выполнить, выглядит принятым и висит
в `QUEUED`, а причина не показана нигде — кадровик будет ждать
индексации, которой не будет.

Случайный вектор вместо настоящего эмбеддинга не подставляется ни при
каких условиях: он ищется как настоящий, и отличить его потом будет
нечем.

## Отправка уведомлений

Строка уведомления создаётся **той же транзакцией**, что и событие, о
котором она сообщает. Откатилась заявка — откатилось и уведомление;
наоборот не бывает.

Забирает сообщения бот, но не из базы напрямую: подключения к PostgreSQL
у него нет и не будет. Он ходит в backend по HTTP с общим секретом,
захват строк делает backend, а бот получает готовый список и сообщает
результат.

Подробности состояний — в `docs/api/hr-crm.md`, раздел «Уведомления».

## Схема OpenAPI

### Как получить

```
# файл
python manage.py spectacular --file schema.yaml

# то же самое, но с проверкой: любое предупреждение — это ошибка
python manage.py spectacular --fail-on-warn --validate --file schema.yaml
```

По HTTP схема всегда доступна на `GET /api/schema`. Читалки
(`/api/docs`, `/api/redoc`) существуют только при `DEBUG=1`: в бою это
лишний открытый интерфейс, который пришлось бы защищать наравне с
остальными.

### Почему ноль предупреждений — обязательное состояние

drf-spectacular умеет строить схему «как получится», молча подменяя то,
что не смог вывести. Такая схема генерируется без сбоя, но описывает не
наш API: у эндпоинта пропадает тело запроса, у параметра — тип, у
способа входа — заголовки. Клиент, сгенерированный по ней, получает
`unknown` вместо типов и шлёт запросы без нужных заголовков.

Поэтому счёт зафиксирован тестом
(`django_tests/test_openapi.py::test_schema_generates_without_complaints`)
и равен нулю. Именно нулю, а не «почти»: один разрешённый недочёт — это
место, куда через полгода добавят второй.

### Что делать, когда тест упал

| Жалоба | Что означает | Как чинить |
| --- | --- | --- |
| `unable to guess serializer` | у `APIView` не описаны запрос и ответ | `@extend_schema(request=…, responses=…)` на метод |
| `could not derive type of path parameter` | нет queryset-а, тип не выводится | для `ServiceViewSet` уже решено в `humotech/core/openapi.py` |
| `could not resolve authenticator` | свой способ входа не описан | `OpenApiAuthenticationExtension`, пример — `humotech/telegram/schema.py` |
| `enum naming ... collision` | одинаково названные поля с разными наборами | запись в `SPECTACULAR_SETTINGS["ENUM_NAME_OVERRIDES"]` |
| `operationId ... has collisions` | два метода дали одно имя | явный `operation_id=` в `@extend_schema` |

Последние две — не косметика: выдуманное имя вроде `Status650Enum`
попадает прямо в типы клиента и меняется от любой правки схемы.
