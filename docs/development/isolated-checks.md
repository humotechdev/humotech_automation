# Изолированные проверки очереди уведомлений

Уведомления — единственная часть системы, которая по своей работе пишет
живым людям в мессенджер. Проверять её «как обычно» нельзя: проверка,
дошедшая до настоящего отправщика, доставляет выдуманное сообщение
настоящему сотруднику, и отозвать его нечем.

Один такой случай уже был. Синтетические уведомления завели скриптом по
рабочей базе, рядом работал настоящий бот, и два сообщения ушли людям.
Предупреждение в документации на тот момент существовало — оно не
помогло. Поэтому ниже описаны не правила поведения, а устройство, при
котором отправить наружу нечем.

---

## Три независимых рубежа

Каждого достаточно поодиночке. Держать проверку на одном нельзя: любой
из них однажды забудут поставить.

| Рубеж | Где | Что делает |
| --- | --- | --- |
| Сеть без выхода наружу | `infrastructure/docker/docker-compose.e2e.yml`, `networks.e2e.internal: true` | у контейнеров стенда нет маршрута в интернет и нет DNS. `api.telegram.org` недостижим физически |
| Отправщик-заглушка | `apps/employee-telegram-bot/src/notifications/sender.py` | `NOTIFICATIONS_SENDER=stub` — доставка не выходит за пределы процесса. Диспетчер aiogram при этом не поднимается вовсе |
| Отказ команды посева | `apps/backend-api/humotech/notifications/isolation.py` | синтетические уведомления не заводятся нигде, кроме изолированной базы |

Проверить первый рубеж можно прямо из контейнера:

```bash
docker exec humotech_e2e_worker python -c "
import socket; s = socket.socket(); s.settimeout(3)
s.connect(('149.154.167.220', 443))"
# OSError: [Errno 101] Network is unreachable
```

## Какая база чем занята

| Кто | База | Кто пишет |
| --- | --- | --- |
| рабочий стенд (`humotech_backend`, `humotech_export_worker`) | `humotech_django` в контейнере `humotech_postgres` | боевой код |
| автотесты (`pytest`) | `test_humotech_django`, Django создаёт и удаляет её сам | тесты |
| изолированный стенд | `humotech_e2e` в **отдельном** контейнере `humotech_e2e_postgres` | сквозная проверка очереди |

Рабочая база и база стенда лежат в разных контейнерах PostgreSQL, на
разных сетях и в разных томах. Перепутать их подключением нельзя: сети
не связаны.

## Отправщик в проверках

`sender.py` знает два отправщика, и выбор делается один раз при запуске:

* `TelegramSender` — настоящая доставка. Единственное место во всём
  проекте, где бот пишет в чат;
* `StubSender` — пишет строку в журнал и отвечает очереди. Наружу не
  ходит вовсе.

Значение по умолчанию — `telegram`, и это намеренно: забытая переменная
должна означать «отправляем по-настоящему», а не молчащую очередь в бою.

`NOTIFICATIONS_STUB_FAIL` перечисляет типы уведомлений, которые заглушка
объявляет неудачными (сравнение по началу строки). Без этого нельзя
проверить ни повтор, ни исчерпание попыток.

**Настоящий токен в стенд не передаётся.** Заглушка сверяет форму
`BOT_TOKEN` и отказывается стартовать, если он похож на настоящий:
заглушка защищает только последний шаг, а всё остальное в этом
процессе — настоящее, и живой токен рядом означает, что стенд подняли
копией рабочего окружения.

## Запрет сетевых вызовов в автотестах

`django_tests/conftest.py` и `apps/employee-telegram-bot/tests/conftest.py`
перехватывают `socket.connect` на всё время сессии. Разрешена только
своя база (адрес берётся из фактической настройки подключения, а не из
имени хоста). Любое другое соединение немедленно проваливает тест с
именем адреса — не молчаливым таймаутом, по которому потом гадают.

Проверка самого предохранителя:
`django_tests/test_notifications_isolation.py::TestNetworkGuard`.

## Сквозная проверка очереди

```bash
cd infrastructure/docker

# 1. поднять стенд (своя база, своя сеть, заглушка вместо Telegram)
docker compose -p humotech_e2e -f docker-compose.e2e.yml up -d

# 2. наполнить: организация, офис, сотрудники, кадровик
docker exec humotech_e2e_backend python manage.py demo_data --yes

# 3. синтетические уведомления и стендовые адресаты
docker exec humotech_e2e_backend \
  python manage.py seed_demo_notifications --with-recipients

# 4. воркер уже работает: он заберёт PENDING, «отправит» заглушкой
#    и отчитается backend тем же HTTP-контрактом, что и в бою
docker logs humotech_e2e_worker | grep STUB

# 5. убрать вместе с томом
docker compose -p humotech_e2e -f docker-compose.e2e.yml down -v
```

Проверка называется сквозной потому, что через неё проходит вся очередь:
`enqueue` → `claim` (`FOR UPDATE SKIP LOCKED`) → HTTP-выдача боту →
доставка → отчёт → `mark_sent` / `mark_failed` → запись попытки. Ненастоящий
в ней ровно один шаг — последний.

Если воркер задания не забрал, проверка сквозной не была, чем бы она ни
кончилась.

## Браузерная проверка CRM на изолированном стенде

Проверка интерфейса требует того же стенда, но с двумя оговорками, из-за
которых её нельзя запустить «просто так».

**Первая: у `backend-e2e` исходники запечены в образ.** Он поднят из
`humotech/backend:local`, и рабочее дерево в него не попадает. Проверять
через него свежий код бессмысленно — он ответит вчерашним. Поэтому рядом
поднимается второй backend с примонтированным деревом.

**Вторая: сеть стенда объявлена `internal: true`.** Маршрута наружу у неё
нет — в этом и смысл, — но вместе с ним нет и способа опубликовать порт
backend на хост. Мостом служит сам контейнер с dev-сервером CRM: он стоит
в двух сетях, публикует свой порт на хост и ходит в backend по внутренней.
Наружу он ничего не отправляет, а backend и воркер остаются без маршрута
наружу — это проверяется одной командой (см. «Три независимых рубежа»).

```bash
# 1. стенд уже поднят (см. «Сквозная проверка очереди»)

# 2. backend с рабочим деревом. Имя БЕЗ подчёркиваний: Django
#    отвергает Host, не проходящий RFC 1034/1035, и запрос через
#    dev-прокси получил бы 400 ещё до всякой авторизации.
docker run -d --name humotech-e2e-live --network humotech_e2e_e2e   -v "$PWD/../../apps/backend-api:/app" -w /app   -e DJANGO_SETTINGS_MODULE=config.settings.e2e   -e DJANGO_DATABASE_URL=postgresql://humotech:humotech_e2e@postgres-e2e:5432/humotech_e2e   -e DJANGO_ALLOWED_HOSTS=backend-e2e,humotech-e2e-live,localhost,127.0.0.1   -e DJANGO_SECRET_KEY=e2e-only-not-a-real-secret-key   -e TELEGRAM_BOT_API_SECRET=e2e-bot-secret -e TELEGRAM_BOT_TOKEN=   -e AI_ASSISTANT_ENABLED=false -e HUMOTECH_TEST_STAND=1   --entrypoint python humotech/backend:local   -m gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 2

# 3. CRM. Адрес НЕ localhost: cookie не различают порт, и вход на
#    стенде снял бы сессию рабочего стенда на localhost:5173.
docker run -d --name humotech_crm_e2e -p 127.0.0.1:5174:5174   -v "$PWD/../../apps/hr-crm:/app" -w /app   -e VITE_BACKEND_ORIGIN=http://humotech-e2e-live:8000   -e VITE_TRUSTED_ORIGIN=http://humotech-e2e-live:8000   node:22-alpine npx vite --port 5174 --host 0.0.0.0 --strictPort
docker network connect humotech_e2e_e2e humotech_crm_e2e

# 4. пароль синтетической учётке. Ввод скрытый: в историю команд,
#    журналы и переписку он не попадает.
docker exec -it humotech-e2e-live python manage.py changepassword tech@humotech.local

# 5. открыть http://127.0.0.1:5174/ и войти
```

`VITE_TRUSTED_ORIGIN` обязан совпадать с тем, во что `changeOrigin`
переписывает `Host`. Django сверяет `Origin` с `request.get_host()`, и
несовпадение даёт «CSRF Failed: Origin checking failed» на первом же
сохранении — отказ, который легко принять за ошибку интерфейса.

Убрать за собой:

```bash
docker rm -f humotech_crm_e2e humotech-e2e-live
```

Стенд и его данные при этом остаются: они нужны другим проверкам.

## Почему команда посева отказывается работать

`seed_demo_notifications` проверяет три вещи и отказывается при любой:

1. `HUMOTECH_TEST_STAND=1` — переменная стенда;
2. имя базы совпадает с `test_*` или `*_e2e`. Список разрешённого, а не
   запрет рабочего имени: запрет ломается в день, когда рядом появляется
   вторая рабочая база;
3. среди действующих привязок Telegram нет ни одной с настоящим
   идентификатором чата. Стендовые адресаты живут в диапазоне
   `1..999` — настоящие идентификаторы туда не попадают даже у самых
   первых аккаунтов, а отрицательные принадлежат группам и каналам, то
   есть тоже настоящим получателям.

Отказ происходит **до первой записи**. Проверяется это тестом, а не
намерением: `test_notifications_isolation.py::TestSeedCommand`.

Того же требует и `config/settings/e2e.py`: он отказывается загрузиться
на базе с рабочим именем.

---

## Чего делать нельзя

* **Отзывать или удалять живые привязки Telegram**, чтобы «обезопасить»
  проверку. Привязка — доступ настоящего человека к своему кабинету;
* **Чистить рабочую очередь**, чтобы получить удобное пустое состояние.
  Пустая таблица после удаления не доказывает, что в ней ничего не было,
  — а настоящие уведомления в ней есть всегда;
* **Останавливать бота вместо изоляции.** Остановленный воркер не
  отменяет заведённые строки: они уйдут при следующем запуске;
* **Помечать уведомление отправленным на рабочем стенде**, если отправки
  не было. Имитация успеха допустима только в изолированной базе.

## Полнота истории попыток

`notifications.attempt_history_complete` — постоянный признак строки, а
не вывод по данным.

Вывести его по данным нельзя. Счётчик `attempts` относится к текущему
циклу повторов и обнуляется при нажатии «Повторить»: у строки, чья
история потеряна, после повтора и счётчик нулевой, и записей нет — ровно
как у только что заведённой.

Признак ставится один раз при заведении строки и не меняется **никогда**:
ни повтор, ни отмена, ни новая записанная попытка не делают утраченное
прошлое известным. В API он приходит как `kept` в ответе
`GET /notifications/{id}/attempts/`, и `kept: false` может прийти вместе
с непустым `items` — это значит «вот что записано, но записано не всё».

Обратное заполнение (`0005_attempt_history_complete`) помечает неполными
только те строки, для которых это установлено достоверно: отправленные
без единой записанной попытки, с ненулевым счётчиком и снятые очередью.
Снятые оператором остаются полными: ручное снятие попыткой доставки не
является и записи не оставляет.

## Права демонстрационной роли

```bash
docker exec humotech_backend python manage.py demo_data --yes
```

Команда идемпотентна и ведёт себя по-разному в двух случаях:

* роль `HR_ADMIN_LOCAL` **создаётся** — выдаётся весь набор `HR_ADMIN`;
* роль **уже есть** — добавляются только разрешения из
  `DEMO_ROLE_REQUIRED` (`notifications.read`, `notifications.manage`).

Синхронизировать существующую роль с каталогом целиком нельзя: это тихо
повысило бы права на всех стендах разом, а «стенд обновили» не значит
«решили выдать больше доступа». Список `NEVER_GRANTED_BY_DEMO`
(`users.manage`, `roles.manage`, `settings.manage`, `audit.read`)
проверяется при загрузке модуля — попадание любого из них в
`DEMO_ROLE_REQUIRED` останавливает команду.

Права других ролей команда не трогает. Разовая вставка в базу больше не
является обязательным шагом запуска стенда.

## Разбор удалённых уведомлений

```bash
docker exec humotech_backend python manage.py restore_deleted_notifications
```

Показывает, каким событиям журнала не соответствует строка очереди, и
ничего не пишет. Набор пропавших строк устанавливается точно: у каждого
уведомления детерминированный `idempotency_key`, собранный из
идентификатора события.

Запись требует `--apply --outcome=SENT|CANCELLED`. `PENDING` среди
исходов нет: возврат истории не должен оборачиваться повторной отправкой.
Время отправки не проставляется даже при исходе `SENT` — его не знает ни
один источник, — а история восстановленной строки помечается неполной.

Перед запуском на рабочей базе проверьте команду на изолированной копии:

```bash
docker exec humotech_postgres pg_dump -U humotech -d humotech_django -Fc > copy.dump
# загрузить в базу с именем вида *_e2e и прогнать там
```
