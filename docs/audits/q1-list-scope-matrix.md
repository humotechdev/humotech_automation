# Вопрос 1. Видимость списков: текущий и предлагаемый доступ

Статус: **матрица на согласование. Реализации нет** (решение владельца 11.10.2026: «списки должны проверять
область конкретного разрешения; не использовать объединённую область, если она расширяет доступ;
реализацию согласовать»).

## Суть

Сейчас чтение списков проверяет **наличие** права где угодно в организации (`access.require(actor, "X.read")`).
Строки при этом отбираются по **объединённой** области всех назначений пользователя
(`visible_office_ids(actor)`, `office_filter(actor)`, `scope(actor)` без кода права).
Записи после этапа 1 уже идут по области конкретного права (`scope_for`).

Предлагается: строки списка = область **того права, которое нужно для просмотра этих данных**
(`visible_office_ids(actor, "X.read")`). Технически это небольшая правка: у всех этих помощников уже есть
параметр `permission`.

**Кого это затрагивает.** Только пользователей с **несколькими назначениями**, у которых права на чтение
лежат в разных областях. Например, «VIEWER на офис A + OFFICE_ADMIN на офис B»: сейчас он видит
посещаемость A через `attendance.read` из OFFICE_ADMIN. Пользователей с одной ролью или с ролями на одной
территории правка не меняет: для одной выдачи `scope_for` совпадает со `scope`.

## Развилка, где нужно ваше решение

**Справочники мест (строка 16).** Офисы, регионы и отделы нужны интерфейсу как **подписи и выпадающие
списки** для других экранов. Если сузить их до `offices.read`, у пользователя из примера пропадёт офис B
в фильтре посещаемости, хотя посещаемость B ему видна по `attendance.read` (если `attendance.read` у него в B).

- **Вариант А (рекомендуется):** справочники мест (название, регион, адрес) — по объединённой области,
  как сейчас. Это метаданные, а не ПДн. Данные о людях (строки 1–15, 17–18) — по области конкретного права.
- **Вариант Б (строго):** всё по области конкретного права, включая справочники. Подписи в списках
  останутся (их отдают сами строки), а фильтры по местам в каждом экране придётся строить из области
  права этого экрана.

**Аналитика (строка 13)** считается по нескольким правам сразу. Предлагается считать по пересечению с
областью `analytics.read`, а блоки с людьми — дополнительно с `employees.read` или `attendance.read`.
Итоги «по организации» тогда честно совпадут с тем, что пользователь видит в списках.

## Последствия и риски

- **Поведение меняется только для пользователей с несколькими назначениями.** Сколько их на рабочем
  стенде, проверить запросом к `user_role_scopes`. Встроенные роли из матрицы ролей выдаются одной
  территорией.
- Обращение «пропали сотрудники/заявки» после выкатки — ожидаемо для таких пользователей. Нужна заметка в
  инструкции HR: видимость теперь задаётся ролью, которая даёт право на этот раздел.
- CRM менять почти не нужно: сервер отдаёт меньше строк. Нужно проверить экраны, которые сами
  ограничивают фильтры по `session.user.permissions`.
- Регрессии: по одному тесту на каждую строку матрицы — «право в A + другое назначение в B → строк B нет»,
  плюс положительный тест для роли на всю организацию.
- Оценка: 1,5–2 дня бэкенда с тестами, около 0,5 дня на проверку CRM.
