# Доступ уволенного сотрудника: текущее поведение и предложение минимального решения

Статус: **предложение на согласование владельцу** (требование 11.10.2026). Код не менялся.
Пути — относительно `apps/backend-api/`. Ключевые утверждения перепроверены оркестратором.

## Требование владельца

С даты увольнения сотрудник теряет доступ к CRM, Telegram-боту и Mini App, если у него не осталось
другого действующего основания для доступа. Учётку и историю не удалять. Предусмотреть увольнение
будущей датой, повторный приём, несколько назначений и отзыв действующих сессий.

## 1. Как сейчас

`terminate()` (`humotech/employees/services.py:933-994`) **сразу** ставит `TERMINATED` и `termination_date`
(дата с сегодняшним днём не сравнивается), закрывает назначения и графики датой увольнения (только начавшиеся
не позже неё — запланированный после даты перевод остаётся открытым) и пишет аудит. `User`, `UserRoleScope`,
сессии, `TelegramAccount`, приглашения — не трогает. Отменить увольнение и повторно принять — нельзя.

| Канал | Увольнение сегодняшней датой | Будущей датой | Где |
| --- | --- | --- | --- |
| CRM, открытая сессия | **работает** (до 24 ч от входа) | работает | `accounts/backends.py:58` — только `user.is_active` |
| CRM, вход по паролю | **работает** | работает | `accounts/backends.py:42-46` |
| CRM-роли | **действуют** | действуют | `accounts/selectors.py:15-28` |
| SSE «Обращения» | работает | работает | `realtime/views.py:110-124` |
| Бот | закрыт | **закрыт сразу, хотя дата не наступила** | `telegram/identity.py:141-146` — по статусу, не по дате |
| Mini App | закрыт со следующего запроса | **закрыт сразу** | `telegram/services.py:1024` → `resolve_account` |
| `TelegramAccount`, приглашения | остаются ACTIVE | остаются | `terminate()` не вызывает `disconnect` |
| Открытые заявки и обращения | не трогаются | — | — |

Повторный приём сейчас невозможен: операции над `FINAL_STATUSES` запрещены (`services.py:81,792,915`),
новая карточка упирается в `uq_employees_org_pinfl`, Telegram ID — в `uq_telegram_accounts_tg_user`.

**Самый опасный разрыв:** уволенный HR сохраняет вход в CRM и роль — видит ПДн сотрудников своей области.

## 2. Основание доступа по коду

- **CRM:** `User.status == ACTIVE`, `archived_at IS NULL`, есть действующая `UserRoleScope`. Сотрудник не учитывается;
  `User.employee` может быть пустым (техническая учётка).
- **Бот / Mini App:** `identity.resolve_account` — привязка ACTIVE, сотрудник не TERMINATED/ARCHIVED, организация ACTIVE,
  есть назначение, действующее сегодня по поясу организации. SUSPENDED доступ не закрывает.
- «Другое основание»: второе назначение (схема допускает, но не создаётся нигде), назначение в другой организации
  (для одного `User` невозможно), учётка CRM без сотрудника, роль, сознательно оставленная владельцем.

## 3. Предложение (минимальное)

1. **Единая функция** `humotech/employees/access.py`: `employment_active(employee, дата_в_поясе_организации)` и
   `crm_access_allowed(user)` = `user.is_active` и (учётка без сотрудника **или** сотрудник ещё работает **или**
   явно разрешённое исключение — см. В2). Дата увольнения — последний рабочий день включительно (как `valid_to`).
2. **Проверка на каждом запросе:** `accounts/backends.py` (`authenticate`, `get_user` — открытая сессия перестаёт
   работать сразу), `realtime/views.py` (SSE), `telegram/identity.py` — блокировать по **дате**, а не по статусу
   (до даты бот и Mini App работают). Свойство `User.is_active` не менять (его используют SQL-фильтры и админка).
3. **`terminate()` будущей датой:** закрыть и назначения, начинающиеся после даты увольнения (или отказать, пока они есть).
4. **Ежедневная задача** `apply_terminations` (по образцу `attendance_reminders --loop`, отдельный сервис compose) —
   только побочные эффекты, доступ закрыт и без неё: `end_sessions`, привязка Telegram и приглашения → REVOKED
   (логику `disconnect` вынести без `actor`), системные записи аудита. Для даты сегодня/в прошлом те же шаги — сразу
   в `terminate()`, в той же транзакции. Идемпотентно, с `select_for_update`.
5. **Не делать:** не удалять `User`/`Employee`/`TelegramAccount`/историю, не ставить `archived_at`, не менять
   `User.is_active`, не отменять автоматически заявки (см. В7).
6. **Отмена увольнения и повторный приём** — новые операции над той же карточкой: `cancel_termination` (до наступления
   даты: ACTIVE, снять `valid_to` с закрытых увольнением периодов — их id сохраняются в аудите `terminate()`),
   `rehire` (ACTIVE, новое основное назначение с `valid_from=hire_date`, новая ссылка Telegram; старые токены
   Mini App уже отсекает `_predates_link`). Исправить сообщение `services.py:917-918`.

Миграции не нужны, если по В2–В4 выбраны варианты (а). Оценка: 2–3 дня бэкенда с тестами + ~1 день CRM
(кнопки «Отменить увольнение», «Принять повторно»).

## 5. Вопросы владельцу

- **В1. Статус при будущей дате:** (а) TERMINATED сразу, доступ по дате — *рекомендовано, меньше правок*; (б) ACTIVE до даты, статус меняет задача (человек остаётся «работающим» в отчётах до последнего дня).
- **В2. Другое основание доступа:** (а) только учётка без сотрудника; (б) + явный флаг «CRM-доступ не зависит от трудоустройства» (миграция); (в) любая действующая CRM-роль — *не рекомендовано*: уволенный HR сохраняет доступ.
- **В3. CRM-роли при увольнении:** (а) не трогать, блокирует функция; (б) закрывать `valid_to` концом дня увольнения (при повторном приёме выдавать заново).
- **В4. `User.status`:** (а) не трогать; (б) LOCKED + поле причины (миграция).
- **В5. CRM-доступ при повторном приёме:** возвращается сам или включает администратор?
- **В6. Сообщение сотруднику «доступ закрыт»:** нужно ли?
- **В7. Открытые заявки и обращения уволенного:** оставить HR, отменить автоматически или пометить?
- **В8. Последний SUPER_ADMIN:** запрещать его увольнение или закрывать доступ?
- **В9. SUSPENDED:** закрывать ли бот и Mini App (сейчас открыты)?
- **В10. Граница дня:** доступ до конца дня увольнения или до его начала?

## 6. Риски

Дополнительный запрос карточки на каждый запрос CRM (`select_related`); расхождение Python-проверки и SQL-фильтров
по `status="ACTIVE"`; изменение `identity` влияет на отмену уведомлений outbox; при В1(б) — все места
`WORKING_STATUSES`; гонка `terminate` и задачи — `select_for_update`.
