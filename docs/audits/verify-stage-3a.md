## Подробности

### B-01 — ПОДТВЕРЖДЕНО, HIGH
- В CRM нет ни одного вызова этих операций. Поиск `terminate|deactivate|reactivate|disconnect|suspend` по `apps/hr-crm/src` нашёл только:
  - деактивацию офисов, регионов, точек и справочников (`api/crm.ts:1176,1220,1295,3030,3062,3108,3156`);
  - отключение учётки CRM (`crm.ts:2437`);
  - подписи событий журнала (`features/employee/card-model.ts:124,148`).
- `revokeOnboardingInvite` (`crm.ts:3738`) отзывает приглашение (`onboarding/services.py:581`), а не действующую привязку.
- Бэкенд эти операции имеет: `employees/views.py:346-365`. Права: `employees.manage` для статуса (`services.py:907`), `employees.archive` для увольнения (`:944`).
- **Неверная деталь.** «Увольнение через админку оставляет уволенного в составе смены и в отчётах» — не так.
  - `roster_assignment_filter` требует `employment_status IN ('ACTIVE',)` (`services.py:105-119`).
  - Человек с TERMINATED, поставленным в админке, из состава и аналитики выпадает.
  - Остаются открытые периоды для тех, кто статус не смотрит: `_covers` (`selectors.py:66-77`), лента, автоматизации.
- **Смягчение.** Админка доступна только SUPER_ADMIN, правки пишутся с префиксом `admin.` (`core/admin.py:1-22, 140-151`). Поле `employment_status` правится, потому что `EmployeeAdmin(OperationalAdmin)` не ограничивает поля (`employees/admin.py:11-20`).
- **Приоритет HIGH оправдан.** Основная кадровая операция недоступна из интерфейса.

### B-02 — ПОДТВЕРЖДЕНО, понизить до MEDIUM
- Как работает:
  - приветствие ставится в очередь в `onboarding.py:233-235` → `lifecycle.py:47-61`, без `scheduled_at`;
  - `claim` (`notifications/outbox.py:221-260`): если привязки нет → CANCELLED `not_linked`;
  - если привязка PENDING или назначение ещё не началось → причина из `resolve_account` (`telegram/identity.py:130-131,152-154`);
  - исключение только для типов `telegram.link.*` (`about_binding`, `outbox.py:225-230`).
- При приёме по ссылке строка `TelegramAccount` появляется только при переходе по ссылке (`telegram/services.py:766-775`). На момент приёма её нет → `not_linked`.
- При подтверждении приветствие повторно не ставится: ставится только `telegram.link.confirmed` (`telegram/services.py:460-468`). Других вызовов `announce_hire` нет (grep: только `lifecycle.py`, `onboarding.py`).
- **Почему MEDIUM.**
  - Данные не теряются. Сотрудник всё равно получает `LINK_CONFIRMED` («Доступ открыт…», `notifications/messages.py:26-29`).
  - Теряется только информационное сообщение о месте работы.
  - Это обещание в комментарии, которое не выполняется, а не сбой кадрового процесса.

### B-06 — ЧАСТИЧНО, MEDIUM
- **Верно.**

  - Ограничения уникальности на телефон в базе нет (`employees/models.py:102-130`).

- Блокировка повторного приёма — следствие отсутствия политики повторного приёма (proposal п.6), а не самостоятельная ошибка.

### B-27 — ПОДТВЕРЖДЕНО (с упущением), MEDIUM
- `terminate` закрывает только периоды с `valid_to IS NULL AND valid_from <= termination_date` (`services.py:974-985`).
- **Упущено в B-27.**
  - Будущий период (запланированный перевод, `valid_from > termination_date`) остаётся открытым.
  - Текущий период, уже закрытый датой перевода `> termination_date`, не обрезается.
  - Это описано в A-35 п.1 и затрагивает B-08.
- Пункт 1 (`EmployeeOfficeAccess`) сейчас без последствий: уволенный не проходит `resolve_account` и отсканировать не может (`identity.py:143-146`). Риск появляется только после возврата статуса через админку.
- Пункт 7 подтверждён: `assignees` проверяет только `User.status` и роль, не офис и не статус сотрудника (`questions/inbox.py:247-271`).
- **Дубли:** A-35 (весь пункт), C-21 (п.2, отсутствия уволенного), C-01 (п.4, открытая сессия).

### B-30 — ПОДТВЕРЖДЕНО, MEDIUM, политика
- Лента берёт область по любому периоду, включая будущие (`notifications/feed.py:1252-1271`). Чтение карточки — тоже (`selectors.py:66-67`).
